## 1. 決定事項

| # | 論点 | 結論 |
|---|---|---|
| 1 | 取得単位 | 4×4束(現行)をやめ、**1×1セル(1次メッシュそのまま)へ戻す**。トランケーション(2,000行)を根本から避ける |
| 2 | リクエスト数上限 | `MAX_CELLS_PER_JOB`(=9、全7レイヤ共通)による「9を超えたら1件も取りに行かない」拒否を、**過去災害/境界の2レイヤだけ外す** |
| 3 | 取得順序 | 視野内で不足/TTL切れのセルを、**中心から近い順(距離でソート)**にキューへ積み、`spawn_job`は今まで通り1個ずつ順次取得(既存メカニズムをそのまま使う) |
| 4 | 描画(広域) | 市区町村ごとの硬い塗り+輪郭線をやめ、**塗りだけ描いた後にボックスブラーを掛ける**。輪郭線は廃止(ブラーが自然な境界を作る) |
| 5 | ブラー強度 | ズームが広くなるほど強く(半径をzに応じて増やす) |

## 2. なぜこれで良いか(会話での検証の要約)

- **速度**: 初回だけ多くのセルを順次取得するコストが掛かるが、取得したセルはTTL(既存30日、必要なら延長)でディスクキャッシュされ、以後は瞬時。「毎回取り直す」ことはない
- **トランケーション**: 1×1セルに戻すことで1セルの行数が実測203件(最混雑)まで下がり、2,000行の上限に対して十分な余裕がある(4×4束の1,223件より安全側)
- **安全弁**: `MAX_CELLS_PER_JOB`は他5レイヤ(交通量/通行規制/主要道路/カメラ/人口メッシュ)には手を付けず、過去災害/境界だけ別扱いにする。他レイヤの安全性は変わらない
- **無限に広域化できるか**: 理論上はできる。1×1セルを中心から近い順に積み続けるだけなので、z9・z5・z1でも同じ仕組みで動く。実務上は「日本全国が同時に必要になるズーム」(z5以下)では取得件数が全国20セル程度で頭打ちになり、むしろ無限に増えることはない(全国のセル数は有限)
- **描画**: 硬い輪郭線が小さい区域で面積の大半を食う問題は、輪郭線を廃止しブラーで境界を滲ませることで解消する。ブラーはフォントのアンチエイリアシングと同じ考え方で、「正確な形」ではなく「読める近似」を作る

## 3. 取得側の実装方針

### 3.1 セル分割を1×1へ戻す

`plotlayer.rs`の`disaster()`/`boundary()`が使う`cells_for`関数(現行は4×4束を返す)を、
1次メッシュ単位(1×1)を返す実装に戻す。`mesh.rs`の広域セル関数(4×4束用に追加したもの)は
他に使い道が無ければ削除するか、テストのみ残すかを実装時に判断する。

### 3.2 `MAX_CELLS_PER_JOB`のレイヤ別扱い

現状は`PlotLayer`共通の`const MAX_CELLS_PER_JOB: usize = 9;`で全レイヤ一律。
過去災害/境界だけ別の上限(または上限無し)にする必要がある。案:

- `PlotLayer::new`に`max_cells_per_job: Option<usize>`引数を追加(Noneなら上限無し)
- 既存5レイヤは`Some(9)`を渡し、disaster/boundaryは`None`を渡す
- 上限が無い場合、`tick()`の該当チェック(`if keys.len() > MAX_CELLS_PER_JOB`)をスキップする

### 3.3 中心から近い順のキュー

`tick()`が`missing`(不足/TTL切れのセルキー一覧)を組み立てる箇所で、各キーのセル中心座標と
現在の視野中心(cx, cy)の距離を計算し、近い順にソートしてから`spawn_job`へ渡す。
`spawn_job`自体(1個ずつ順次取得・都度`CellMsg::Loaded`を送る)は変更不要で、
渡す配列の順序を変えるだけで実現できる。

セルキーから中心座標を逆算する関数が要る(`mesh.rs`側に、セルキー→bboxの逆変換が既にあるはず。
無ければ追加する)。

### 3.4 上限を外すことで起きうる懸念と対応

- 一度に非常に多くのセルが不足する場面(初回起動・大ジャンプ検索等)では、`spawn_job`のスレッドが
  長時間動き続ける。既存の「1個ずつ順次・都度メッセージ」の仕組みにより、UIはブロックされず、
  取れたセルから順に描画が更新される(現行のtick()のループがそのまま対応する)
- パン/ズームで視野が変わるたびに`missing`を再計算するため、ユーザーが動き続ける限り「常に今見ている
  近くから先に埋まる」形になる(優先度の再計算が自然に効く)
- ジョブが1本しか同時に走らない制約(`if self.job.is_some() { return; }`)は現状維持。
  複数ジョブを並列化する変更は今回のスコープ外(直列でも「近い順」があれば体感は十分改善する)

## 4. 描画側の実装方針

### 4.1 輪郭線の廃止とブラーの導入

`choropleth::build_layer`の`Shading { fill, outline }`から`outline`関連の描画
(`stroke_rings_rgba`呼び出し)を削除する。

`fill_rings_rgba`で塗った後の`RgbaImage`に対し、新規関数`blur_rgba(img: &mut RgbaImage, radius: u32)`
を適用する。ボックスブラーを採用する理由:

- ガウシアンブラーより実装・計算コストが低い(分離可能・O(W×H)の累積和で実装できる)
- 見た目の違いは境界の滲み方の質だけで、地図の縮小表示という用途では十分

アルファチャンネルも含めて(色×アルファの事前乗算形で)ブラーを掛けることで、記録の無い
市区町村(透明)との境界も自然に滲む。

### 4.2 ブラー半径のズーム依存

`radius = blur_radius_for_zoom(z)`のような関数を用意し、z9で小さい半径(例: 1〜2px)、
zがさらに小さくなるほど半径を大きくする(例: z7で3px、z5で5px、のような段階)。
具体的な値は実装時に実際の画面で見ながら調整する(数値を先に決め切らない)。

### 4.3 braille/edgeモードとの整合

braille/edgeは既に`InkLayer::Stipple`で点描を通しており、ある程度「ぼんやり」した見た目に
なっている。ブラーを追加で掛けるかは実機で見て判断する(既に十分ぼんやりしていれば不要)。
