肥大化した `src/ui.rs` の `interactive()` を分割できる状態にするための設計。
機能追加は含まない(挙動を変えないリファクタ)。

## 1. 現状(実測。2026/08/17 時点)

- `src/ui.rs` は 2624 行。そのうち `interactive()` が 39〜2622 行で、ファイルのほぼ全部が
  1関数。ユニットテストは1件も無い(`#[cfg(test)]` が無い唯一のモジュール)。
- `interactive()` の先頭 41〜195 行 + 372〜387 行で **ローカル変数が約110個**宣言される。
  内訳は画面状態(focus/各リストの選択行)・地図位置(cx/cy/z)・ルート(wps/spec/mode)・
  16個のバックグラウンドジョブ受信口(`Option<Receiver<..>>`)・5枚のプロットレイヤ・
  再生/レーダー/GPS の状態・再emit抑制の記録など。
- `macro_rules!` は**定義5個・呼び出し23箇所**。
  `restart_prefetch_on_zoom!` `radar_turn_on!` `radar_toggle!` `sync_roads!` は数行だが、
  `run_action!`(236〜362行・127行)は `MenuAction` 28種の実処理本体で、上のローカル変数を
  40個以上そのまま参照している。マクロにしているのは「関数に切り出すと引数が40個を超えるから」
  という消極的な理由で、この5個が切り出しの物理的な壁になっている。
- キー処理は `match cur { Focus::… }` の **28分岐(1530〜2563行)**。最大の `Focus::Map` が
  264行、`Focus::Settings` が84行。
- ジョブ完了の取り込みは1箇所にまとまった **277行(1093〜1369行)**。
- 同じ内容の重複が既に発生している。ジョブが動いているかの判定
  `route_job.is_some() || search_job.is_some() || …`(13〜16項)が**4箇所**、
  全ジョブを畳む `xxx_job = None;` の羅列が**2箇所**。機能を1つ足すたびに
  「宣言」「ジョブ判定4箇所」「取り込み」「キー処理」「設定画面の行」へ配線が増える。

## 2. 採る設計: 状態を1つの構造体に集める(`UiState`)

`src/uistate.rs` に `UiState` を作り、`interactive()` のローカル変数(端末ハンドル `out`・
タイルローダー `loader`・端末復元用の `TermGuard` を除く全部)をフィールドとして持たせる。
`interactive()` は `let mut st = UiState::new(a, cx, cy, z);` で始め、以降は `st.foo` を触る。

理由:

1. **切り出しの前提条件がこれしか無い。** 「Focusごとのキーハンドラ関数化」は目的としては
   正しいが、状態が裸のローカル変数のままだと関数の引数が40〜60個になるので実現できない。
   マクロを使っているのも同じ理由。状態を1つにまとめると
   `fn on_key_map(st: &mut UiState, env: &mut Env, fc: &FrameCtx, k: KeyEvent)` という
   4引数に落ちる。つまり `UiState` 化は「Focusごとの関数化」の対立案ではなく前提。
2. **この方式は既にこのリポの流儀。** 描画側は切り出し済みの
   `ui_gutter::GutterCtx` / `ui_status::StatusCtx`(フィールド参照を並べた文脈構造体)へ
   状態を渡す形になっている。読み取り専用の描画には参照の構造体、書き換えを伴うキー処理と
   ジョブ取り込みには `&mut UiState`、と揃える。
3. **テストが書けるようになる。** 今の `interactive()` は端末とネットワークに触るので
   1行もテストできない。状態が構造体になれば、`radar_toggle` のような状態遷移を
   「入力の状態→出力の状態」として直接検証できる。

採らなかった案:

- **状態をグループ別の小構造体に分ける(`Jobs` / `RadarState` / `PlayState` …)**:
  ジョブ判定の重複は消えるが、ジョブ取り込み処理は完了時に `spec`・`focus`・`addr`・`pois`
  など「ほぼ全部」を書き換えるので、結局まとめた文脈が必要になる。個人開発の規模で
  階層を2段にすると `st.play.speed` のような書き換えが全体に波及するだけで得が無い。
  ただし `UiState` の中はコメントで区切って並び順をグループにしておく。
- **キーハンドラだけ関数化して状態はローカルのまま**: 上記1のとおり不可能。

## 3. 分け方と段取り

1つのコミットで全部やらない。各段でビルドとテストが通る状態にする。

1. `UiState` 追加 + `interactive()` の全参照を `st.` へ機械置換 + 小さいマクロ4個を
   `UiState` のメソッドへ(`run_action!` はこの段ではマクロのまま `st.` を触る)。
2. `run_action!` → `ui_action::run_action()`。フレーム値は `FrameCtx` で受ける。
3. ジョブ取り込み277行 → `ui_jobs::poll()`。ジョブ判定の重複4箇所も
   `UiState::jobs_active()` に寄せる。
4. `match cur { Focus::… }` 28分岐 → 関心ごとにファイルを分けたキーハンドラ関数群。
5. 各段で切り出した関数にユニットテストを足す。

`interactive()` に残すのは「1フレームの流れ」(端末サイズ取得 → 早期return画面 →
レイヤのスライス → 地図生成 → 描画 → ジョブ取り込み → 入力待ち → キー配送)だけにする。

## 4. 挙動を変えないための約束

- フレーム内の順序(キー入力 → 状態更新 → 描画、`polling` によるポーリング間隔の決定)は
  そのまま。切り出しは「その場に書いてある処理を関数の中へ移す」だけに限る。
- ループを抜ける処理(`Focus::Map` の `quit` と終了確認の `break`)は、関数化にあたって
  戻り値でループ側へ返す(`break` を関数の中に隠さない)。
- PTY実機での確認はこの作業環境では出来ないので、`cargo build --release` の警告0件と
  既存テスト(572 + 18件)の全通過を毎段で確認する。
