## 1. 何を見せるか、誰がいつ見るか

機能一覧を作る前に使われ方から決める。termmap はツーリング用の地図なので、人口メッシュは
統計を眺めるためではなく**走る前・走っている最中の判断材料**として要る。

| 場面 | 知りたいこと | メッシュ人口が答えること |
|---|---|---|
| ルートを引く前 | この先に補給(コンビニ・給油・宿)が期待できるか | 人がいる帯とゼロの帯がそのまま出る |
| 夜間・林道の計画 | 明かり・人・電波が無い区間はどこか | 人口ゼロのメッシュが連続する範囲 |
| 市街地の回避 | 混む市街をどこで迂回するか | 高密度メッシュの塊 |
| 走りながらの興味 | この谷はなぜ家が少ないのか | 過疎の分布が地形と重なって見える |

ここから「使われ方から自明に出てくる要件」が3つ出る。仕様の都合ではなく利用の都合なので、
設計の制約として最初に置く。

- **通信量を利用者が予期できること。** 1都道府県が最大31MB(§2.2)。ツーリング中はテザリングが
  普通なので、パンした拍子に無言で31MB落ちる作りにはできない。既定OFF・取得中の明示・
  1度取ったら数年再取得しない、の3点が必須。
- **中断に強いこと。** 取得は都道府県まるごとで数十秒かかる。途中でアプリを閉じても、
  次に開いたときに続きから使える(=ディスクに残る)必要がある。逆に取得中に画面が止まっては
  いけない(既存レイヤと同じくワーカースレッドへ出す)。
- **地図が読めなくなってはいけないこと。** 人口は面を塗る唯一のレイヤになる。全面を不透明で
  塗ると道路も経路も消える。塗りは必ず半透明かディザで、濃さは設定で下げられること。

表示の主語は「メッシュ1枚の推計人口」ではなく**その土地の人口密度**にする。500mメッシュは
0.25km²なので、メッシュ人口×4 が 人/km² になる。密度にすると縮尺や地域が変わっても
色の意味が変わらず、凡例が1つで済む。

## 2. 実測で分かったデータの形(2026/08/17、実ファイル)

### 2.1 ダウンロードURL(確定)

一覧ページ `https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-mesh500r6.html` は DataTables で
表を組み立てるが、**zipへの相対パスは静的HTML中に文字列として存在する**(JSはソート・絞り込みを
しているだけで、行そのものはサーバー側で埋め込まれている)。そこから採取した実URLは次の形。

```
https://nlftp.mlit.go.jp/ksj/gml/data/m500r6/m500r6-24/500m_mesh_2024_{PP}_GEOJSON.zip
```

- `{PP}` = JIS X 0401 の都道府県コード2桁(`01`〜`47`)。ゼロ埋め必須。
- `{PP}` を `52`〜`59` にすると地方ブロック単位(東北・関東・甲信越北陸・東海・近畿・中国・
  四国・九州)、`_{PP}` ごと省くと全国1本になる。いずれも都道府県より大きいので使わない。
- `GEOJSON` を `SHP` / `GML` に替えると同じ体系で別形式が取れる。GeoJSON を採る
  (§2.3 のとおり幾何も属性も1ファイルで完結し、追加の解析器が要らない)。
- ディレクトリの `m500r6-24` は「R6推計・2024年公開」を指す版番号。**次の推計が出たら変わる**
  ので、コード上は定数1つに切り出しておく(§5.2 `DATASET_DIR`)。

実アクセス確認: `01` / `13` / `31` の3件を実際に取得し、いずれも `HTTP 200` /
`Content-Type: application/zip` を確認済み。認証・Referer・Cookie は不要。

### 2.2 サイズと件数(実測)

| 都道府県 | zip | 展開後 GeoJSON | メッシュ件数 | 2次メッシュ数 |
|---|---:|---:|---:|---:|
| 北海道(01) | 31,541,743 B (30.1MB) | 276,998,583 B (264MB) | 40,544 | 823 |
| 東京(13) | 8,588,212 B (8.19MB) | 41,462,584 B (39.5MB) | 5,447 | 55 |
| 鳥取(31) | 4,713,440 B (4.50MB) | 28,958,174 B (27.6MB) | 4,083 | 52 |
| (参考)全国 | 511MB | ― | ― | ― |

一覧ページ掲載の47都道府県のzipは 4.21MB(沖縄)〜30.1MB(北海道)。**北海道が最悪ケース**で、
zip 30MB・展開264MB・4万件。全国1本(511MB)は端末アプリの取得単位として現実的でない。

ここから2つの設計上の帰結が出る。

- 展開後が264MBある以上、**JSON文字列を丸ごとメモリへ載せてはいけない**。zipの展開と
  JSONの解析をストリームで繋ぐ(§5.3)。
- 30MBの取得は一瞬では終わらない。取得中であることを画面に出し、一度取ったら長く持つ(§6.2)。

### 2.3 GeoJSONの中身

```
FeatureCollection
  name: "500m_mesh_2024_31"
  crs : urn:ogc:def:crs:EPSG::6668   (JGD2011 地理座標)
  features[]:
    geometry  : Polygon / 外環1本 / 頂点5点(閉じた矩形)  ← 全件がこの形
    properties: 343個
```

- 幾何は**全件が軸平行の矩形**(50,074件を検査して例外なし)。凹多角形も穴も島も無い。
- 座標系は EPSG:6668(JGD2011)。termmap が使う WGS84 との差は日本国内で数cm〜1m未満で、
  z18(1px≒0.6m)でも1px未満。変換せずそのまま使う。
- メタデータXML(`KS-META-...xml`)は **CP932** で入っている。GeoJSON本体は UTF-8。
  本体しか読まないので実装には影響しないが、手で開くときは注意。

### 2.4 MESH_ID から矩形が計算できる(検査で完全一致)

`MESH_ID` は9桁の**2分の1地域メッシュコード**(JIS X 0410 の3次メッシュを4分割したもの)。
桁の意味と矩形の導出は次のとおり。

```
MESH_ID = p p u u  r c  r3 c3  q      例: 523351132
          └1次┘   └2次┘└3次┘ └500m┘
  lat0 = p/1.5 + r/12 + r3/120 + ((q-1)/2) / 240      (整数除算)
  lon0 = 100+u + c/8  + c3/80  + ((q-1)%2) / 160
  高さ = 1/240 度 (緯度15秒) / 幅 = 1/160 度 (経度22.5秒)
  q: 1=南西 2=南東 3=北西 4=北東
```

北海道・東京・鳥取の全 **50,074 件**について、この式で求めた矩形と GeoJSON の実座標を
比較して**差 1e-6 度以内での不一致は0件**。q は 1〜4 の全値が実在する。

つまり**幾何は保存しなくてよい**。9桁のコード1つから矩形が完全に復元できる。
1件あたり頂点5点(f64×10 = 80バイト)を捨てて `u32` 1つ(4バイト)にできるので、
キャッシュサイズもメモリも1桁下がる。既存の `src/mesh.rs` は1次/2次までしか持っていないので、
500mメッシュぶんをここへ足す(§5.1)。

### 2.5 秘匿処理(HITOKU / GASSAN)と、PTN と PT00 の使い分け

属性には秘匿処理の痕跡が入っている。鳥取県2025年で `HITOKU2025` は `*` が271件・`@` が255件・
null が3,557件。意味は実データの算術で確定した。

- `*` … このメッシュは秘匿対象。`PT00_*` が 0 にされ、人口は `GASSAN*` が指すメッシュへ移される。
- `@` … 秘匿対象を受け取った側の合算先メッシュ。
- `PTN_*` … 合算前の**そのメッシュ自身の値**。
- `PT00_*` … 合算後の**公表値**。

実例(鳥取・2025年):

```
523351153  HITOKU='*'  GASSAN=523351151  PTN=1.7394  PT00=0.0
523351151  HITOKU='@'  GASSAN=null       PTN=28.5645 PT00=30.3039
                                          28.5645 + 1.7394 = 30.3039  (完全一致)
```

**地図の塗りには `PTN_*` を使う。** 理由は、`PT00_*` だと秘匿対象のメッシュが人為的に0になり、
その隣が人為的に膨らむため、「人がいない帯」が実際とは違う場所に出るから。鳥取の2025年では
`PTN` の0は57件だが、`PT00` ではそこへさらに271件の人工的な0が乗る。地理的な正しさが要る用途に
`PT00` は向かない。県単位の合計はどちらでも一致する。

一方で**年齢階級の値は `PT00` 系である**ことに注意する。`PT01_*`〜`PT20_*` の合計は
`PT00_*` と一致し(500件検査して不一致0)、`PTN_*` とは一致しない(500件中124件が不一致)。
比率 `RTA`〜`RTE` も `PT00` 基準。したがって高齢化率を表示する場合、秘匿対象メッシュ
(`PT00=0`)では比率が意味を持たないので**「データなし」として塗らない**。

### 2.6 年次と属性

年次は `2020` と `2025`〜`2070` の5年刻み(計11時点)。2020年は令和2年国勢調査に基づく実績で、
**総数 `PTN_2020` しか無い**(年齢階級・比率は2025年以降のみ)。原典の推計は250mメッシュで
行われ、500mメッシュへ集計されている。

| 属性 | 意味 |
|---|---|
| `MESH_ID` | 2分の1地域メッシュコード(9桁) |
| `SHICODE` | 行政区域コード5桁。上2桁が都道府県コード(1ファイル=1都道府県を実測で確認) |
| `PTN_20XX` | 総数人口(合算前) |
| `PT00_20XX` | 総数人口(合算後・公表値) |
| `PT01_20XX`〜`PT20_20XX` | 5歳階級別人口(0〜4歳 … 95歳以上) |
| `PTA/PTB/PTC/PTD/PTE_20XX` | 0〜14 / 15〜64 / 65以上 / 75以上 / 80以上 の人口 |
| `RTA/RTB/RTC/RTD/RTE_20XX` | 同じ区分の構成比 |
| `HITOKU20XX` / `GASSAN20XX` | 秘匿記号 / 合算先メッシュコード |

分布(`PTN_2025`、メッシュ1枚あたりの人数):

| | 中央値 | 90%点 | 99%点 | 最大 |
|---|---:|---:|---:|---:|
| 北海道 | 7.1 | ― | 1,867 | 6,062 |
| 東京 | 2,217 | 5,926 | 8,486 | 15,796 |
| 鳥取 | 32.7 | 335 | 1,402 | 2,144 |

密度に直すと(×4) 28人/km² 〜 63,000人/km²。**3桁半の幅がある**ので、色分けは
線形では潰れる。対数的な階級を切る(§7.4)。

## 3. zipの展開をどうするか

GeoJSONはzipでしか配られない。termmap は現在 `flate2` も `zip` も直接依存していないが、
`Cargo.lock` を見ると **`flate2 1.1.9` は既に依存ツリーに入っている**
(`image` → `png` → `flate2`)。つまり `Cargo.toml` の `[dependencies]` に `flate2 = "1"` を
足しても、**ビルドに新しいサードパーティのコードは1行も増えない**。既に
コンパイルされているものを直接参照できるようにするだけ。

zipコンテナ自体は自前で読む。`zip` クレートは新規の依存になるうえ、必要なのは
ローカルファイルヘッダを1つ読む処理だけで済むため。実ファイルで構造を確認した。

```
PK\x03\x04 | ver | flag=0x0000 | method=8(deflate) | ... | crc32 | csize | usize | nlen | elen
           → 名前(nlen) → 拡張(elen) → 生 deflate ストリーム(csize バイト)
```

- 3エントリ(ディレクトリ / .geojson / .xml)とも `flag=0x0000`。**データディスクリプタが無く、
  ローカルヘッダの時点で `csize`/`usize`/`crc32` が確定している**ので、中央ディレクトリを
  読まずに先頭から順に辿れる。
- `.geojson` は `method=8`(deflate)。`flate2::read::DeflateDecoder`(zlibヘッダ無しの生
  deflate)がそのまま使える。
- 検証: 手書きのヘッダ解析で切り出した deflate ストリームを展開した結果が、
  `unzip` の出力と **SHA-256 で一致**。CRC32 も宣言値と一致。

実装は「先頭から順にローカルヘッダを読み、名前が `.geojson` で終わる最初のエントリを
`DeflateDecoder` へ渡す」だけでよい。ヘッダの `usize` を上限チェックにも使う(zip爆弾よけに
展開後サイズが 512MB を超えるものは拒否する)。

代替案として自前 inflate の実装も考えられるが、既にビルドへ入っている実装があるのに
同じものを書き直す理由が無い。

**この節は `Cargo.toml` の変更を伴うので、実装着手前にユーザーの承認が要る。**

## 4. どの都道府県のファイルが要るかの判定

### 4.1 都道府県のbboxでは判定できない

素直に「都道府県ごとの外接矩形の表を持ち、視野と交差するものを取る」とやると壊れる。
東京都のデータの実測bboxは次のとおり。

```
東京(13): 緯度 24.292 〜 35.850 / 経度 138.988 〜 153.981
鳥取(31): 緯度 35.083 〜 35.608 / 経度 133.150 〜 134.488
```

小笠原・南鳥島まで含むため、東京の外接矩形は**沖縄と同じ緯度帯から日付変更線の手前まで**を覆う。
これで判定すると、沖縄本島を見ているだけで東京(8.19MB)を取りに行く。北海道・鹿児島・
長崎も同様に離島で矩形が伸びる。外接矩形は使えない。

### 4.2 2次メッシュ → 都道府県 の索引を持つ

判定は矩形ではなくメッシュコードで行う。**2次メッシュ(約10km四方)から都道府県コードへの
索引**を静的データとして持ち、視野を覆う2次メッシュ(既存の `mesh::secondary_codes`)を
引いて都道府県の集合を得る。

```
視野bbox → mesh::secondary_codes() → 索引 → 都道府県コードの集合(重複除去)
```

- 2次メッシュは約10km四方。z11の視野でも数枚に収まり、跨る都道府県は通常1〜2件。
- 索引は人口メッシュデータ自身から作れる。各 feature は `MESH_ID`(上6桁が2次メッシュ)と
  `SHICODE`(上2桁が都道府県)を両方持っているため、両者の直積を取ればよい。
- 都道府県境を跨ぐ2次メッシュは複数の都道府県を持つ。索引は**過剰側に倒す**
  (交差する可能性のある都道府県は全部載せる)。取りすぎは通信の無駄で済むが、
  取りこぼしは県境の帯がまるごと欠ける。

サイズの実測: 北海道・東京・鳥取の3県ぶんで **930行 / 9,300バイト**(1行約10バイト)。
北海道だけで823行あり、これが全国土の約22%にあたるので、全国では **5,000〜6,000行 /
50〜60KB程度**と見込む。`include_str!` で埋め込み、初回参照時に `HashMap<u32, Vec<u8>>`
へ展開する。

```
data/mesh2pref.csv     533946,13,14
                       523351,31
```

**索引の生成**は開発時の一度きりの作業として `src/bin/gen-mesh2pref.rs` に置く。
47ファイル(合計約480MB)を順に取得し、`(MESH_ID[0..6], SHICODE[0..2])` を集めて重複を除き、
ソートして CSV へ書く。生成物 `data/mesh2pref.csv` はリポジトリへコミットする。
再生成が要るのは推計の版が上がったとき(数年に1度)だけ。本体と同じストリーム解析(§5.3)を
使って、264MBのファイルでもメモリを食わないようにする。

索引に無い2次メッシュ(人口メッシュが1枚も無い海上・無人の山域)は、都道府県が引けないので
何も取得せず何も描かない。これは正しい振る舞いで、原典にもデータが無い。

## 5. データ層 `src/population.rs`(新規)

### 5.1 型

```rust
/// 500mメッシュ1枚ぶんの推計人口。幾何は持たない(MESH_ID から復元できる・§2.4)。
pub struct PopMesh {
    /// 2分の1地域メッシュコード(9桁)。u32 に収まる(最大 999,999,999 < u32::MAX)。
    pub mesh: u32,
    /// 総数人口(PTN_*、合算前)。索引は YEARS と同じ並び(2020,2025,…,2070 の11要素)。
    pub pop: [f32; 11],
    /// 65歳以上の構成比(RTC_*)。2025〜2070 の10要素。2020年に年齢別の値は存在しない。
    /// 秘匿対象メッシュ(PT00=0)では意味を持たないので f32::NAN を入れる。
    pub aged: [f32; 10],
}

pub const YEARS: [u16; 11] = [2020, 2025, 2030, 2035, 2040, 2045, 2050, 2055, 2060, 2065, 2070];
```

`f32` で足りる。原典の値は小数4桁までの推計値で、最大でも16,000程度。`f32` の有効桁は
7桁あるので丸め誤差は表示に出ない。

`mesh.rs` へ足す関数:

```rust
/// 9桁の2分の1地域メッシュコード → (lat_min, lon_min, lat_max, lon_max)。
pub fn half_mesh_bbox(code: u32) -> (f64, f64, f64, f64);
```

`primary_bbox` / `secondary_bbox` と同じ場所・同じ流儀で置く(std だけに依存し、
ネットワークにもcrateにも触れない)。

`PlotItem` の実装はこれを呼ぶだけになる。

```rust
impl PlotItem for PopMesh {
    fn bounds(&self) -> Bbox { mesh::half_mesh_bbox(self.mesh) }
}
```

### 5.2 保持する項目の選択

343個の属性のうち何を残すかで、キャッシュとメモリが決まる。実データで両案を計測した。

| 案 | 保持する内容 | 構造体 | JSON(北海道) | JSON(東京) | 全国見込み |
|---|---|---:|---:|---:|---:|
| full | PTN×11年 + RTC×10年 | 88 B/件 | 4.64MB | 0.85MB | 約73MB |
| slim | PTN×3年(2020/25/50) + RTC×1年 | 24 B/件 | 1.78MB | 0.28MB | 約27MB |

**full を採る。** 判断の根拠は、高いのは通信であって保存ではないこと。北海道は
**31MBを落として4.6MBを残す**か **31MBを落として1.8MBを残す**かの選択で、2.8MBを惜しんで
項目を捨てると、後から別の年を見たくなったときに31MBを取り直すことになる。
節約する側が間違っている。

一方で 5歳階級別(`PT01`〜`PT20`)と `PTA`/`PTB`/`PTD`/`PTE`、`PT00` 系は**捨てる**。
端末の面塗りはメッシュ1枚につきスカラー1つしか表現できないので、20階級を持っても
描きようが無い。年齢の内訳を出すのは別機能(メッシュを選んで詳細を出す)であり、
そうなったときに設計し直す。

全国73MBはあくまで「47都道府県すべてを訪れた場合の上限」で、`plotcache` の
`max_bytes` で頭打ちにする(§6.2)。

### 5.3 ストリームでの展開と解析

264MBを文字列に載せないため、zip展開とJSON解析をリーダーで直結する。

```
ureq のレスポンス本体(Read)
  → 全体をメモリへ(最大31MB。zipの解析にはヘッダの先読みが要るため、ここは載せる)
  → ローカルヘッダ解析(§3)で .geojson の deflate ストリームの範囲を決める
  → flate2::read::DeflateDecoder
  → std::io::BufReader
  → serde_json::Deserializer::from_reader → 型付き構造体へ
```

要点は3つ。

- **zipは載せる / GeoJSONは載せない。** zip側は最大31MBで許容範囲。展開後の264MBは
  `from_reader` で逐次読むので、常駐するのは `Vec<PopMesh>`(北海道で3.6MB)だけになる。
- **型付きで受ける。** serde の derive は**未知のフィールドを割り当てずに読み飛ばす**ので、
  343個中の21個だけを `#[serde(rename)]` で拾えば、残り322個は文字列にすらならない。
  `serde_json::Value` で受けると343個ぶんの `String` と `Value` が全件で確保されて破綻する。
- **幾何は読み飛ばす。** `geometry` は `serde::de::IgnoredAny` で受ける。頂点5点の配列を
  4万件ぶん確保しない。矩形は `MESH_ID` から作る(§2.4)。

属性は年ごとにフィールド名が変わる(`PTN_2025` … `PTN_2070`)ので、derive で21個の
フィールドを並べるか、`properties` を `HashMap<String, serde_json::Value>` ではなく
カスタム `Visitor` で舐めてキー名から年を切り出すかの二択になる。**derive で21個並べる**方を
採る。年次の一覧は5年ごとに固定されていて増減しないので、マクロや動的解決を持ち込むより
21行書いたほうが読める。

参考時間: Python の `json.load` で北海道が7.5秒(全343属性を辞書化するため)。Rust の
型付きストリーム解析は読み飛ばしが効くのでこれより速くなるが、**それでも数秒かかる前提**で
UI を作る(§6.3・§7.6)。

## 6. `PlotLayer<T>` への統合

### 6.1 セル単位 = 都道府県コード

取得元が都道府県単位でしかファイルを分けていないので、セルもそれに合わせる。
既存レイヤ(1次メッシュ / 2次メッシュ / 地方整備局)と同じく「取得元が持つ自然な単位」に
揃えるという `plot-data-disk-cache-design.md` §4 の方針どおり。

```rust
fn population_cells(b: Bbox) -> Vec<String> {
    population::prefectures_for(b).iter().map(|p| format!("{p:02}")).collect()
}
```

キーは `"01"`〜`"47"`。`plotcache::valid_key`(英数字と `-` `_`、16文字以内)を満たす。

### 6.2 TTL と上限

```rust
Layer::Population => 365 * DAY   // fresh_ttl
Layer::Population => None        // stale_limit
Layer::Population => 47          // max_entries
Layer::Population => 96 * MB     // max_bytes
```

- **fresh 365日**: 推計の改定は数年に1度(前版が令和2年国勢調査ベース、公開2024年12月)。
  他レイヤの最長は主要道路・過去災害の30日だが、それより2桁近く動きが遅い。
  31MBの再取得を年1回より頻繁に起こす理由が無い。
- **stale上限なし**: 古い推計が誤りになることはない。新しい版が出て置き換わるだけ。
- **max_entries 47**: 都道府県は47しかない。これ以上のキーは原理的に生じない。
- **max_bytes 96MB**: full 案の全国見込み73MB(§5.2)に余裕を持たせた値。到達したら
  `gc` が取得の古い順に削り、必要になれば取り直す。

版が上がったときの扱い: URL の `m500r6-24`(§2.1)が変わるので、`plotcache` の
`FORMAT_VERSION` を上げて旧データを一掃するのが確実。年1回の fresh 切れを待つより、
版を上げたコードのリリースで確実に切り替わる。

### 6.3 ズーム下限とセル数

`min_zoom = 11` にする。既存の交通量・通行規制・過去災害と同じ値で、複数レイヤを同時にONに
したときに「このレイヤだけ端が欠ける」状態にならない。

メッシュ1枚が画面上で何pxになるかで確かめる(緯度35度・`geo::meters_per_pixel`)。

| ズーム | m/px | メッシュ1枚 | 判断 |
|---|---:|---:|---|
| z10 | 125.2 | 4.0 px | braille で4×4ドット(2桁×1行)。ディザで間引くと隣接階級が判別できない |
| z11 | 62.6 | 8.0 px | braille で8×8ドット(4桁×2行)。階級差が塊として読める |
| z12 | 31.3 | 16.0 px | はっきり読める |
| z14 | 7.8 | 63.9 px | 1枚が大きく、境界が目立つ |

z11 が下限として妥当。それ未満では取得も描画もしない(既に持っているセルは残す)。

セル数は `MAX_CELLS_PER_JOB = 9` の枠内で問題ない。z11の視野が跨る都道府県は最大でも
3〜4件(関東・近畿の県境付近)。

### 6.4 `plotlayer.rs` / `plotcache.rs` への追加

必要な変更は4点。うち1点は既存レイヤの挙動を変えないための小さな一般化。

1. `plotcache.rs` に `Layer::Population` を足す。`dir_name` = `"population"`、
   `ALL_LAYERS` を6要素へ、TTL・上限は §6.2。

2. **`MAX_CELLS_IN_MEMORY` をレイヤごとの値にする。** 現在は定数32で全レイヤ共通。
   人口メッシュは1セルが北海道で3.6MB あるため、32セルだと最悪 100MB を超える。
   `min_zoom` や `data_lag_secs` と同じく `PlotLayer` のフィールドにして
   `new()` で受け取り、人口は **4** にする(4件で最悪14MB)。他レイヤは32のまま渡すので
   挙動は変わらない。

3. `plotlayer.rs` に組み立て関数を足す。

```rust
/// 500mメッシュ別推計人口(国土数値情報)。都道府県単位・z11未満では取得しない。
/// メモリ保持は4県まで(1県が最大3.6MBあるため他レイヤの32とは別枠)。
pub fn population() -> PlotLayer<population::PopMesh> {
    PlotLayer::new_with_cap(Layer::Population, 11, 0, 4, population_cells, fetch_population_cell)
}
```

4. **取得中のセルを名前で出せるようにする(任意・Stage2)。** 現在 `job_active()` は
   真偽値だけで、どのセルを取っているかは分からない。他レイヤは1セルが1秒未満なので
   それで足りていたが、人口は1セルに数十秒かかるため「何を待っているのか」が要る。
   `CellMsg` に `Started(String)` を足し、`PlotLayer` が `fetching_key()` を持てば、
   ステータス行に「人口 北海道を取得中…」と出せる。既存レイヤは送らなければ影響しない。

### 6.5 検討した代替案: 2次メッシュをセルにする

「セル=2次メッシュ(約10km)、取得時に都道府県まるごと落として2次メッシュごとに切り分けて
保存する」案も検討した。比較は次のとおり。

| 観点 | 案A: セル=都道府県(採用) | 案B: セル=2次メッシュ |
|---|---|---|
| 通信量 | 同じ(取得元の最小単位が都道府県) | 同じ |
| メモリ | 1セルが最大3.6MB。上限を4に下げる必要 | 1セル約400件。既存の32のまま収まる |
| `items()` の走査 | 最大4県×4万件 = 16万件/描画 | 最大32セル×400件 = 1.3万件/描画 |
| ディスク | 47ファイル | 全国で約5,000ファイル |
| 必要な改造 | メモリ上限のレイヤ別化(小) | 1回の取得で複数セルを書く仕組み(大)。`scratch` の型変更か、取得関数から `plotcache::store` を直接叩く層の飛び越えが要る |

**案Aを採る。** 通信量は同じで、案Bが優るのは描画時の走査だけ。その走査も16万件×単純な
矩形交差判定で1描画あたり1ミリ秒未満に収まり、しかも termmap は毎フレームではなく
表示状態のハッシュが変わったときだけ再構築する(`ui.rs` の `map_sig`)。案Bの複雑さに
見合わない。走査が実際に問題になったら、そのときに案Bか空間索引へ移す。

## 7. 表示

### 7.1 描画経路は雨雲レーダーと同じ

面を半透明で塗るレイヤは既に1つある。雨雲レーダー(`radar.rs` + `render.rs`)で、
そこで確立した経路をそのまま使う。

```
population レイヤ → RgbaImage(出力寸法・人口なし=透明)
  ├ 実画像/halfblock: blend_rgba_over(&mut img, &layer, opacity)   … 地図が下に透ける
  └ braille/edge   : ink_*_into_overlay(&mut ov, &layer, …)        … Bayerディザで間引いたインク
```

`OverlayLayer` へ直接 `draw_polygon_fill` する案は**採らない**。`OverlayLayer` は不透明な
1色インクで、面を塗ると下の地図が完全に消える(§1 の3つ目の制約に反する)。線やマーカーには
適しているが、面の塗りには向かない。面は `RgbaImage` を作って合成する。

重ね順は **人口 → 雨雲 → リング → 経路 → 道路 → マーカー**。人口は数年変わらない下地、
雨雲は現況なので、人口を最背面に置く。

### 7.2 `render.rs` へ足す塗りつぶし関数

```rust
/// RgbaImage の軸平行な矩形を塗る。範囲外はクリップする。x1/y1 は半開区間(含まない)。
pub fn fill_rect_rgba(layer: &mut RgbaImage, x0: i32, y0: i32, x1: i32, y1: i32, color: [u8; 4]);

/// RgbaImage の多角形を塗る(偶奇規則のスキャンライン)。凹多角形も可。穴は扱わない。
pub fn fill_polygon_rgba(layer: &mut RgbaImage, pts: &[(i32, i32)], color: [u8; 4]);
```

500mメッシュは全件が軸平行の矩形(§2.3)なので、**#77 が使うのは `fill_rect_rgba` だけ**。
毎回スキャンラインを回す理由が無い(1描画で数千枚を塗るため、単純なループのほうが速い)。

`fill_polygon_rgba` は #77 では使わないが、面を塗るレイヤは今後も出る。
`docs/weather-warning-overlay-design.md` §3 の気象警報(class10s の発表区域ポリゴン)が
そのまま該当し、行政区域やハザードマップも同じ形になる。**共有できる形で今のうちに置く**か、
**使うときに書く**かは判断が要る。

推奨は **`fill_rect_rgba` だけを実装し、`fill_polygon_rgba` は書かない**。使う当てが
確定していない汎用関数を先に置くと、最初の実利用者が現れたときに要件(穴あき・
自己交差・アンチエイリアス・ワインディング規則)が合わずに書き直すことになる。
上の署名は#79が着手するときの出発点として設計に残す。

### 7.3 braille / edge のインク密度

`ink_radar_into_overlay` は「アルファが閾値以上の画素を、一定密度でディザして置く」もので、
アルファの大小は密度に反映されない。雨雲は降水あり=不透明・なし=完全透明の2値なので
それで足りていた。人口は階級ごとにアルファを変える(§7.4)ため、**密度をアルファで変調**したい。

```rust
// 変更前: 一定密度 d でディザ
if (BAYER4[y % 4][x % 4] as f64) >= d * 16.0 { continue; }
// 変更後: 画素のアルファで変調
if (BAYER4[y % 4][x % 4] as f64) >= d * 16.0 * (p[3] as f64 / 255.0) { continue; }
```

**雨雲の挙動は変わらない。** 雨雲のアルファは 0 か 255 の2値なので `p[3]/255` は常に 1 になる。
既存のテスト(`ink_density_matches_designed_coverage` 等)は全画素アルファ255のレイヤで
書かれているため、そのまま通る。

あわせて関数名を `ink_rgba_into_overlay`、`RadarInk` を `InkLayer` へ改名するのが素直だが、
`ui.rs` と `render.rs` の両方に手が入る。**現在 `ui.rs` は他の作業と衝突しやすい状態にある**ため、
改名は実装時に他の変更が落ち着いてから、あるいは名前は据え置いて呼ぶだけにする。

`build_overlay` の引数は `radar: Option<RadarInk>` の1本しか無いので、人口ぶんを足す
(`population: Option<InkLayer>` の追加、または `inks: &[InkLayer]` へまとめる)。
`ui.rs` の呼び出し1箇所と `render.rs` のテスト2箇所に影響する。

### 7.4 階級と配色

**階級は視野に依存しない固定値**にする。視野内の分布で正規化すると、パンするたびに同じ土地の
色が変わって読めなくなる。凡例も出せない。

指標は人口密度(人/km² = メッシュ人口 × 4)。7階級。

| 階級 | 人/km² | 色(RGB) | アルファ | 目安 |
|---:|---|---|---:|---|
| ― | データなし / 0 | 塗らない | ― | 無人・海・山 |
| 1 | 〜100 | 250,232,245 | 40 | 山間・過疎 |
| 2 | 100〜1,000 | 232,190,230 | 80 | 農村・集落 |
| 3 | 1,000〜4,000 | 208,140,210 | 120 | 郊外の住宅地 |
| 4 | 4,000〜10,000 | 176,92,186 | 160 | 地方都市の市街 |
| 5 | 10,000〜20,000 | 138,52,150 | 200 | 大都市の住宅密集 |
| 6 | 20,000〜 | 96,20,110 | 230 | 都心部 |

意図は3点。

- **色相は紫〜マゼンタ。** 地図の分類色(`render.rs` の `cat_color`)が 水=青 / 緑地=緑 /
  幹線=黄 / 建物=ベージュ を使い、雨雲は気象庁配色(青→緑→黄→赤)を使う。人口が虹色だと
  雨雲と混ざる。単一色相の明度変化にすると「これは雨ではない」が一目で分かる。
  鉄道が紫(180,95,200)だが、あちらは細い線でこちらは面なので混同しない。
- **薄い階級はアルファも低い。** 人口の少ない土地はほとんど透けたままになり、地図が読める。
  人が多い場所だけが浮き上がる。ツーリング中に見たいのは「ここから先に人がいるか」なので、
  この非対称は望ましい。
- **アルファは設定の濃さで一律に掛かる**(`blend_rgba_over` の `opacity` がレイヤのアルファに
  掛け算される)。雨雲の light/mid/strong と同じ仕組みをそのまま使う。

境界値は「〜100」を100未満、「100〜1,000」を100以上1,000未満とする(下側を含む)。

### 7.5 指標は Stage1 では人口密度だけ

`Metric::Aging`(高齢化率)と `Metric::Change`(2020年比の増減率)も型としては置くが、
**Stage1 では実装しない**。理由は配色が未決だから。

- 高齢化率は 0〜100% の単調な量なので密度と同じ単一色相ランプで出せるが、密度と同じ紫だと
  どちらを見ているのか分からなくなる。別色相が要る。
- 増減率は正負に分かれるので発散配色になる。標準的な青⇔赤は水域・雨雲と衝突し、
  緑⇔赤は緑地と衝突する。衝突しない2色を決める必要がある。

どちらも「実際に密度を画面で見てから決めたほうが早い」種類の判断なので、Stage1 を出してから
決める。`class_of()` の署名に `metric` を入れておけば、追加時に呼び出し側は変わらない。

### 7.6 ステータス行と凡例

`ui_status.rs` の `plot_label` と同じ流儀で1項目足す。アイコンは 👥 。

```
👥取得中…              レイヤON・まだ何も無い
👥北海道を取得中…      §6.4 の Started が入った場合
👥1,240人/km²          中心のメッシュの密度(通常時)
👥人口データ無し       索引に無い(海上・無人域)
👥広域では非表示       z11未満(suppressed)
```

**中心のメッシュの実数値を出す**のが要点。色分けだけだと階級の幅(1,000〜4,000等)しか
分からないが、termmap は中心にクロスヘアがあるので、そこの数値を出せば正確な値が読める。
`half_mesh_bbox` の逆算(緯度経度→メッシュコード)でハッシュを1回引くだけで済む。

凡例は常時出すと画面を食う。ヘルプ(`?`)の中に階級表を置く。

## 8. データ量の見積りと対策

「500mメッシュは数千〜数万件になりうるので間引きが要るのでは」という懸念について、
実測から確認した結果を書く。**結論として間引きは要らない。**

### 8.1 実際に画面へ出る枚数

描画の解像度 `(rw, rh)` は AA モードなら端末の出力ピクセル数、実画像モードなら
`map_cols × scale` × `map_rows × 2 × scale`。200桁×50行の端末で braille なら約 400×200 px、
実画像モード(high)で約 800×400 px。

| ズーム | メッシュ1枚 | 400×200 の画面 | 800×400 の画面 |
|---|---:|---:|---:|
| z11(下限) | 8.0 px | 約 1,250 枚 | 約 5,000 枚 |
| z12 | 16.0 px | 約 300 枚 | 約 1,250 枚 |
| z14 | 63.9 px | 約 18 枚 | 約 72 枚 |

最大でも5,000枚。1枚あたりの塗り面積を合計しても**画面の総ピクセル数(320,000)を超えない**
(矩形が画面を隙間なく敷き詰めるだけなので)。全面塗り1回ぶんのコストしかかからない。

### 8.2 効いている対策(いずれも既存の仕組み)

1. **ズーム下限 z11**(§6.3)。z10以下はメッシュが braille の4×4ドットまで縮み、
   ディザで間引いた時点で隣の階級と区別できなくなる。ここで切るのが間引きより素直。
2. **`items(view)` の矩形交差フィルタ**。既存の `PlotLayer::items` がそのまま使える。
   `bounds()` が `half_mesh_bbox` を返すので、視野外のメッシュは描画対象に入らない。
3. **メモリ保持セル数を4に**(§6.4)。最悪16万件・14MB で頭打ち。
4. **人口0・データなしは塗らない**。鳥取で `PTN_2025` が0のメッシュが57件、
   そもそもデータに存在しないメッシュ(無人域)はもっと多い。

### 8.3 やらないこと

- **ズームに応じた間引き(2×2 の集約等)は入れない。** §8.1 のとおり塗りのコストは
  画面サイズで頭打ちになるので、集約しても速くならない。むしろ集約すると境界が
  1kmグリッドへずれて、地形との対応が読めなくなる。
- **視野内での動的な正規化は入れない**(§7.4)。

実際に描画が重いと分かったら、そのときに測ってから対策する。今の見積りで先回りして
機構を足す理由が無い。

## 9. 設定

`config.rs` の既存パターン(`radar_enabled` / `radar_opacity` / `traffic_enabled` …)に揃える。

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `[population] enabled` | bool | `false` | 起動時にONにするか |
| `[population] opacity` | `light`/`mid`/`strong` | `mid` | 塗りの濃さ。雨雲と同じ 0.35/0.55/0.75 |
| `[population] year` | 2020〜2070 の5年刻み | `2025` | 表示する年次 |

**既定OFF** は他の外部データレイヤと同じ理由(ONにした人だけが外部サービスへ問い合わせる)に
加えて、§1 の通信量の制約からも必須。

`[population] metric` は §7.5 のとおり Stage2 で足す。`year` は不正値を既定へ落とす
(`radar_opacity` が `light`/`mid`/`strong` 以外を弾いているのと同じ扱い)。

設定画面(`settings.rs`)には3行足す。**設定行を足したら `ui.rs` の Enter キー分岐にも
配線が要る**(過去に配線漏れの事故があり、ユニットテストでは検出できない。PTY実機で
実際にトグルして確認すること)。

キー割り当ては、雨雲の `C` に倣って1文字を割り当てる。`P` は未使用かを `keymap.rs` で
確認してから決める。

## 12. テスト方針

ネットワークに触れないものを単体テストにし、実データが要るものは手順として残す。

- `half_mesh_bbox`: §2.4 の既知値。`523351132` → 矩形が
  `(35.0916666, 133.16875, 35.0958333, 133.175)`。q=1〜4 の4通り。
  1次/2次メッシュとの入れ子関係(500mメッシュ4枚が3次メッシュ1枚を覆う)。
- zipのローカルヘッダ解析: 手で組んだ最小のzipバイト列で、名前・method・csize が
  読めること。method が 8 以外・展開後サイズが上限超過なら拒否すること。
- GeoJSONの解析: 実ファイルから切り出した2〜3 feature ぶんの断片を固定文字列にして、
  `PTN_*` と `RTC_*` が並び順どおりに入ること。343属性のうち未知のものが読み飛ばされること。
  秘匿対象(`PT00=0`)で `aged` が NaN になること。
- `prefectures_for`: 索引の既知の行から、東京の視野で `13` が出ること。
  小笠原の緯度帯で東京**以外**が出ないこと(§4.1 の外接矩形では壊れるケース)。
- 階級判定 `class_of`: 境界値(100 / 1,000 / 4,000 / 10,000 / 20,000 人/km²)の
  上下と、0・データなし。
- `fill_rect_rgba`: 画面外へのクリップ、幅0・高さ0、負座標、左右逆転した引数。
- インクのアルファ変調: **既存の雨雲テストが1行も変わらずに通ること**が回帰の要
  (§7.3)。加えてアルファ128の画素が255の画素より点数が少ないこと。
- `plotcache`: `Layer::Population` の往復と、365日のTTL境界。

実データが要る確認(手順として残す):

- 鳥取(31)を実取得して 4,083 件になること。
- 北海道(01)を実取得して 40,544 件になること、および取得中にUIが止まらないこと。
- PTY実機で設定のトグルが効くこと(ユニットテストでは検出できない・過去に事故あり)。
- braille / halfblock / 実画像の3モードで、地図が読める濃さになっていること。
  「テストが通った」を「見た目が正しい」の証拠にしない。

## 13. 制約・未検証

- **索引の全国生成は未実施。** 3県ぶん(930行)で形式とサイズ感を確認しただけで、
  全国5,000〜6,000行という見込みは外挿。実際の行数と、都道府県境を跨ぐ2次メッシュの
  割合(3県では0件だったが、これは3県が互いに隣接していないため)は生成して初めて分かる。
- **Rust側の解析時間は未計測。** Python の `json.load` で北海道7.5秒という値しか無い。
  型付きストリーム解析はこれより速いはずだが、実測していない。数秒で済まないなら
  ステータス表示(§6.4-4)は任意ではなく必須になる。
- **`ureq` でのストリーム取得は未検証。** §5.3 は zip 全体をメモリへ載せる前提で書いたが、
  31MB のレスポンスを `ureq` がどう扱うか(タイムアウト・途中切断時の挙動)は確認していない。
  長距離移動中の回線断でどうなるかは実機で見る必要がある。
- **配信元への負荷。** 47ファイル合計480MBの取得を索引生成で1度行う。開発時に1回きりで、
  利用者側は訪れた都道府県ぶんだけなので過大ではないが、生成スクリプトは
  1件ずつ直列に取り、User-Agent を名乗る。
- **`ui.rs` は現在ほかの作業と衝突しやすい。** §6.4-4 の改名や `build_overlay` の
  引数変更は、着手時点の状況を見てから入れる。
- **年齢構成の表示(§7.5)と、メッシュを選んでの詳細表示は設計していない。**
  必要になったら別途。データ側(§5.2)では `RTC` を保持しているので、取り直しは要らない。
- タスク #77 後半の「視認性重視の設定項目を増やす」はこの設計に含まない。
  面レイヤが増えることで地図の情報密度が上がるため関連はするが、
  透明度・表示密度・フィルタの拡充は複数レイヤ横断の課題として別に扱う。
