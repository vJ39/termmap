iPhone(web版)の地図ドラッグが「まだ不自然・斜めがガタつく」件の原因調査と改善設計。
タスク#87(`docs/web-touch-drag-design.md`・実装済み)の続きで、#87 が解決した「ゲインが指と合わない」
「送ったキーが捨てられる」の先にある、コマ送り感と階段状の動きを対象にする。

対象コード: `src/ui.rs`(描画ループ・再描画判定) / `src/tiles.rs`(窓の切り出し) / `src/render.rs`(AA描画) /
`src/dragmode.rs`(比→ピクセル換算) / `web/touch-overlay.js`(送信レート・慣性)。
状態: 設計のみ。実装は未着手。

## 1. 症状

#87 のあと、iPhone でのスワイプについて次の指摘が出ている。

- 縦・横だけでなく斜めやいろいろな角度の動きをもっと滑らかにしてほしい
- 体験が悪い

#87 で入った仕組み(指の移動量を比で送り、Rust 側で地図の出力ピクセルへ換算して合算適用)自体は
狙いどおり動いている。後述のとおりゲインは実測で 1.00 倍。残っているのは「1:1 で正しい位置に着く」
ことと「動きが滑らかに見える」ことが別問題だという点。

## 2. 実測

推測で切り分けると外すので、先に数字を取った。

### 2.1 計測方法

`target/release/termmap` を PTY 上で起動し(端末サイズを固定・`TERM_PROGRAM=iTerm.app`・
`COLORTERM=truecolor`・`HOME` は一時ディレクトリへ逃がして保存状態を触らない)、
ブラウザが送るのと同じ形式の bracketed paste

```
ESC[200~ \u{1}PAN\u{1}<fx>\u{1}<fy>\u{1} ESC[201~
```

を流し込んで、termmap が吐く出力バイト数・フレーム数・ステータス行の緯度経度を読む。
スクリプトは作業用ディレクトリに置いたもので、リポジトリには入れていない(§9 で常設テストの形へ落とす)。

端末サイズは 94×23(iPhone 横持ちの目安)、90×45、44×50 の3種で取った。地図は z14・
経由地なし(左袖なし = `map_cols` は端末幅そのまま)。

### 2.2 1フレームのバイト数

| 端末 | 描画モード | PAN 1回あたりの出力 | 30Hz で流したときの出力 |
|---|---|---|---|
| 90×45 | halfblock(既定) | 163,168 B | 4.35 MB/s |
| 90×45 | braille | 61,746 B | 1.63 MB/s |
| 94×23 | halfblock | 85,611 B | 2.28 MB/s |
| 94×23 | braille | 34,185 B | 0.91 MB/s |
| 44×50 | halfblock | 89,383 B | 2.39 MB/s |
| 44×50 | braille | 36,291 B | 0.94 MB/s |
| 94×23 | 実画像(mid) | 75,747 B | 0.48 MB/s(約7コマ/秒しか出ない) |
| 94×23 | 実画像(high) | 262,381 B | 0.61 MB/s(同上) |

halfblock は1セルあたり前景SGR+背景SGR+`▀` で約41バイト。braille は前景SGRのみ+点字1文字で
約22バイト、インクが無いセルは空白1バイトなので、同じ画面で 2.5 倍安い。

実画像モードだけ挙動が違い、PNG エンコードが重くて 30 回の PAN に対し 7 コマ程度しか生成できない。
このときは Rust 側の合算(`src/ui.rs:1434-1449`)が効いて位置は正しいまま、コマだけ落ちる。

### 2.3 サブピクセル移動でも全画面を再送している

1出力ピクセルの 1/100 しか動かない PAN(`fx=fy=0.0001`)を 94×23 halfblock で 10 回連続で送った結果:

```
 1:   85642 bytes  sha1=8d210605a7f7
 2:   85642 bytes  sha1=6717dc9e99ad
 3:   85642 bytes  sha1=6717dc9e99ad   ← 2〜5 は完全に同一バイト列
 4:   85642 bytes  sha1=6717dc9e99ad
 5:   85642 bytes  sha1=6717dc9e99ad
 6:   85640 bytes  sha1=d9040ea9a434   ← 6〜9 も互いに同一
...
```

地図の絵が1ピクセルも変わっていないのに、毎回 85.6KB の全画面書き換えが出ている。
`map_sig`(`src/ui.rs:757`)が `rcx.to_bits()` / `rcy.to_bits()` を混ぜているため、
`build_window_nowait` の切り出しが `(left - tx_min*TILE) as u32`(`src/tiles.rs:589`)で
整数へ丸められて結果が同じでも、シグネチャだけが変わって `need_build`(`src/ui.rs:809`)が立つ。

ゆっくり指を動かしているときほど、この「同じ絵の再送」の割合が上がる。

### 2.4 見えるコマ数は「読み手の処理能力 ÷ 1フレームのバイト数」で決まる

読み手(ブラウザ相当)をトークンバケツで絞り、30Hz のスワイプ1秒間に termmap が実際に出せた
コマ数を測った。

| 読み手の処理能力 | halfblock(85.6KB/コマ) | braille(34.1KB/コマ) |
|---|---|---|
| 無制限 | 25.0 コマ | 25.9 コマ |
| 4.0 MB/s | 26.0 コマ | 24.9 コマ |
| 2.0 MB/s | 25.0 コマ | 25.9 コマ |
| 1.0 MB/s | 13.0 コマ | 25.9 コマ |
| 0.5 MB/s | 7.0 コマ | 15.9 コマ |

ttyd は pty から読んだ塊を WebSocket へ送り切るまで次を読まないので、ブラウザが遅れると
termmap 自身が出力で止まり、その間に届いた PAN が入力側で溜まって合算される。
結果、位置は正しいまま**コマだけが間引かれる**。スワイプ1秒で 7 コマなら、地図は 7 回の
大きな飛びで動く。これが「コマ送りで不自然」の正体。

halfblock が 30Hz を維持するには 2.2MB/s、braille なら 1.0MB/s の処理能力が要る。
Cloudflare Tunnel 経由の iPhone Safari + xterm.js がこれを満たすかは実機で測る必要があるが、
満たしていない側に倒れているとみるのが自然。

### 2.5 ゲインは 1:1(ただし1組み合わせだけ2倍)

ステータス行の緯度経度から、`fx=fy=0.5`(端末の半分を横切る)1回ぶんの実移動量を測った。

| 描画モード | 実測 dx | 期待 dx | ゲイン | 実測 dy | 期待 dy | ゲイン |
|---|---|---|---|---|---|---|
| halfblock | 46.6 | 47.0 | 0.99x | 22.9 | 23.0 | 1.00x |
| braille | 94.4 | 94.0 | 1.00x | 45.9 | 46.0 | 1.00x |
| halfblock + 実画像 | 46.6 | 47.0 | 0.99x | 22.9 | 23.0 | 1.00x |
| **braille + 実画像** | **94.4** | **47.0** | **2.01x** | **45.9** | **23.0** | **2.00x** |
| braille + 実画像(high) | 94.4 | 47.0 | 2.01x | 45.9 | 23.0 | 2.00x |

単位は z14 の世界ピクセル。braille(または `--edge`)と実画像モードを同時に有効にすると、
両軸とも指の2倍動く。原因は §3.3。

## 3. 仮説の検証

### 3.1 仮説1「テキストグリッドの量子化」— 半分正しい。ただし縦横の非対称ではない

各モードで地図が動ける最小単位は次のとおり(`src/ui.rs:560` と `src/ui.rs:687-692`)。

| モード | 出力ピクセル寸法 | 横の最小移動 | 縦の最小移動 |
|---|---|---|---|
| halfblock(既定) | `(map_cols, map_rows*2)` | 1文字セル | 1/2文字セル |
| braille / edge | `(map_cols*2, map_rows*4)` | 1/2文字セル | 1/4文字セル |
| 実画像 low(=移動中は常にこれ) | `(map_cols, map_rows*2)` | 1文字セル | 1/2文字セル |
| 実画像 mid(既定・静止時) | `(map_cols*2, map_rows*4)` | 1/2文字セル | 1/4文字セル |
| 実画像 high(静止時) | `(map_cols*4, map_rows*8)` | 1/4文字セル | 1/8文字セル |

文字セルの縦横比はおよそ 1:2 なので、CSS ピクセルに直すと横と縦の粒度はどのモードでもほぼ等しい
(braille の 2×4 ドット・halfblock の 1×2 ピクセルは、もともとこの比に合わせてある)。
つまり「縦と横で量子化の粒度が違うから斜めが荒れる」という前提は成り立たない。

斜めだけ目立つ理由は別で、**X と Y が独立に切り捨てられる**ことにある。
`build_window_nowait` は `left` と `top` をそれぞれ別に整数化するので、描かれる位置の誤差は
X 成分と Y 成分が無関係に ±1ピクセル未満で揺れる。

- 真横のドラッグ: 誤差は進行方向と平行。速度のむらにしか見えない。
- 斜めのドラッグ: 誤差に進行方向と直交する成分が乗る。地図が進行方向の左右へ振れて、
  軌跡が階段状に見える。

人間の目は「進行方向のブレ」より「進行方向と直交するブレ」にはるかに敏感なので、
同じ量子化でも斜めだけが目立つ。指摘の内容と一致する。

加えて、既定の halfblock は横の最小移動が丸ごと1文字セル(iPhone の xterm.js 既定フォントで
おおむね 9 CSS ピクセル前後・要実測)なので、ゆっくり動かすと「9px 動かないと1回も動かず、
超えたら 9px 飛ぶ」という見え方になる。粒度そのものが粗い。

### 3.2 仮説2「送信レート30Hzと描画更新頻度」— これが最大の要因

`PAN_MIN_INTERVAL_MS = 33`(`web/touch-overlay.js:71`)で送るところまでは意図どおり出ている。
Mac 側の生成能力も 30Hz を満たしている(§2.2 の「無制限」列)。

問題は §2.4 のとおり、見えるコマ数がブラウザの処理能力とフレームサイズの比で決まる点。
端末のストリームには「古いフレームを捨てて最新だけ描く」という概念が無いので、
ブラウザは受け取ったぶんを全部順に描くしかない。したがって

```
スワイプ中に見えるコマ数 ≒ ブラウザが1秒に処理できるバイト数 ÷ 1フレームのバイト数
```

が上限になる。1フレームを半分にすればコマ数は倍になる。逆に言うと、送信レートを上げても
描画方式を変えても、この比を改善しない限り滑らかにはならない。

なお termmap 側の合算処理は入力の取りこぼしを防ぐが、出力の詰まりには効かない。
出力が詰まっている間は termmap のループ自体が止まるので、その間の PAN は入力側で溜まり、
再開時にまとめて1コマで消化される。

### 3.3 仮説3「X軸Y軸の非対称」— 換算式は正しい。ただし1組み合わせにバグがある

`pan_ratio_to_px`(`src/dragmode.rs:134-143`)は

```
dx = fx * cols * (ow / map_cols)
dy = fy * rows * (oh / map_rows)
```

で、左袖の有無・標高帯の有無に関係なく 1:1 になる。実測でも 1.00 倍(§2.5)。左袖が出ていても
`ow/map_cols` は 1(halfblock)か 2(braille)の定数なので比率は崩れない。ここは問題ない。

一方、実画像モードでは実際に描かれる解像度が `ow/oh` ではなく `rw/rh`(`src/ui.rs:689-691`)で、

```
rw = map_cols * scale,  rh = map_rows * 2 * scale,  rz = z + delta
```

となる。表示している地理範囲は zoom z 換算で常に横 `map_cols` ピクセル・縦 `map_rows*2` ピクセル
なので、1:1 にするには `ow=map_cols` / `oh=map_rows*2` を使わなければならない。ところが
`src/ui.rs:1452` で `dragmode::Layout` に渡しているのは AA 用に計算された `ow/oh` で、
`opts.braille`(または `opts.edge`)が立っていると `map_cols*2` / `map_rows*4` になる。
その結果、braille + 実画像の組み合わせだけ両軸2倍になる。§2.5 の実測どおり。

指の2倍動くので「指から地図が逃げる」感覚になり、方向は正しいぶん原因に気づきにくい。
ユーザーがこの組み合わせを使っている場合、これ単独でも体験が悪い理由として十分。

### 3.4 仮説4「モード別の体感差」

§3.1 の表のとおり、粒度は halfblock が最も粗く、braille で半分、実画像 mid/high でさらに細かい。
バイト数は §2.2 のとおり braille が halfblock の 40%。したがって

- braille は「粒度が細かい」「バイトが安い(=コマ数が増える)」の両方で halfblock より有利。
- 実画像は静止時の粒度は最も細かいが、`image_settle_low_res` の既定 true により
  **移動中だけ scale=1 に落ちる**(`src/ui.rs:680,687`)。滑らかさが要る瞬間に一番粗い状態になる。
  さらに PNG エンコードでコマ数が 7/秒まで落ちる。

既定は halfblock(`src/config.rs` の `braille=false` / `image_mode=false`)なので、
何も設定していない iPhone ユーザーは一番粗くて一番高いモードを使っていることになる。

### 3.5 仮説5「その他」

読んで見つかったもの。いずれも単独では主因ではないが、体感を落としている。

| 箇所 | 内容 |
|---|---|
| `web/touch-overlay.js:790` `passedTapSlop` | スロップ(12px)を超えた瞬間、`panLast` が開始点のままなので 12px 超がまとめて1回で送られる。指を動かし始めた瞬間に地図が飛ぶ |
| `web/touch-overlay.js:87,730` 慣性 | `GLIDE_TICK_MS = 60`(約16Hz)の `setTimeout` で動かしている。指を離した後の動きが 16 コマ/秒のコマ送りになる |
| `web/touch-overlay.js:71,481` 送信タイミング | 33ms 固定タイマーで、画面のリフレッシュと位相が合わない。iOS は負荷時にタイマーをまとめて発火させるので、送信間隔が不揃いになる |
| `web/touch-overlay.js:467` `terminalViewportSize` | フラッシュのたびに `getBoundingClientRect()` を呼ぶ。touchmove 中に毎回同期レイアウトを起こす |
| `web/touch-overlay.js:69,104` フォールバック | OSC 9997 を1度も受け取れないと `dragModeSeen` が false のままで、見た目は同じまま従来の 24px 量子化キー方式に留まる。#87 が丸ごと効いていない可能性がある |

最後の1点は実機で最初に確認すべき。Safari の開発者ツールから
`__termmapTouch.getDragAxes()`(§10)で判別できる。

## 4. 原因の順位

| 順位 | 原因 | 効き方 | 対策 |
|---|---|---|---|
| 1 | 1フレームが大きすぎてコマ数が落ちる(§2.4, §3.2) | 全方向。コマ送り感の主因 | 対策B・C・D |
| 2 | 描画位置が出力ピクセル単位で切り捨てられ、X/Y が独立に飛ぶ(§3.1) | 斜めで直交方向のブレになる。指摘の「斜めが不自然」に直結 | 対策A |
| 3 | 既定 halfblock の粒度が横1文字セルと粗い(§3.1) | ゆっくり動かすと階段状 | 対策A・C-2 |
| 4 | サブピクセル移動で同じ絵を再送している(§2.3) | 遅いドラッグほど無駄が増える | 対策B |
| 5 | braille + 実画像でゲイン2倍(§3.3) | その組み合わせのときだけ致命的 | 対策E |
| 6 | ドラッグ開始の12px飛び・慣性16Hz・タイマー駆動(§3.5) | 開始と終了の印象を落とす | 対策F |

## 5. 対策設計

### 5.1 対策A: サブピクセル描画(階段を消す)

**やること**: 地図画像を「切り捨てた整数位置」ではなく「小数位置」で作る。

`window_tile_range`(`src/tiles.rs:222`)が返す `left`/`top` の小数部を捨てずに使う。
`build_window_nowait` を

1. `(win_w + 1) × (win_h + 1)` を整数位置で切り出す
2. `fx = left.fract()`, `fy = top.fract()` を重みに 2×2 のバイリニアで `win_w × win_h` へ落とす

という形にする。追加のタイル取得は不要(同じ zoom のタイルのまま)で、計算量は
`win_w * win_h` に対する掛け算4回。94×22 で 2,068 ピクセルなので無視できる。

**効果**: 出力セルの色が連続的に変化するので、1セル未満の動きも色の遷移として見える。
X と Y が同時に連続になるため、§3.1 の直交方向のブレが消える。halfblock のまま
実効的な滑らかさが braille や実画像に近づく。

**注意**: braille / edge は輝度の閾値でドットの on/off を決める(`src/render.rs:55-118`)ので、
バイリニアで作った中間色が閾値をまたぐ瞬間にドットが入れ替わる。実質ディザになるため、
階段は消えるがちらつきが増える可能性がある。halfblock と実画像では素直に効く。
braille は実機で確認して、悪ければ braille だけ従来の整数切り出しに戻せるようにしておく。

**副作用**: 描画結果が `left`/`top` の小数部に依存するようになるので、対策B の量子化単位を
「整数ピクセル」ではなく「サブピクセルの刻み」で決める必要がある(§5.2)。

### 5.2 対策B: 同じ絵なら送らない

**やること**: `map_sig`(`src/ui.rs:757`)に `rcx.to_bits()` / `rcy.to_bits()` をそのまま混ぜるのをやめ、
実際に描画へ効く粒度へ丸めた値を混ぜる。

- 対策A を入れない場合: `rcx.floor()` / `rcy.floor()`(切り出しが整数なので、これで過不足なし)
- 対策A を入れる場合: サブピクセルの刻みを定数で決めて `(rcx * SUBPIXEL_STEPS).round() as i64`
  (`SUBPIXEL_STEPS` は 8 か 16 を想定。実機で詰める)

あわせて、`build_window_nowait` / `build_overlay` へ渡す中心座標も同じ丸めを通した値にする。
描画に使う位置とシグネチャの位置がずれると、絵が変わるのにシグネチャが変わらない取りこぼしが起きる。
論理座標 `cx`/`cy` は連続のまま保持し、丸めるのは描画へ渡す直前だけにする。

**効果**: §2.3 の完全に無駄な全画面再送が消える。ゆっくりドラッグでのバイト数がそのぶん減り、
対策C と合わせてコマ数の底上げになる。

**注意**: `map_sig` にはオーバーレイ(経路・POI・雨雲)の状態も混ざっているので、
そちら起因の再描画は今までどおり走る。ここで変えるのは中心座標の項だけ。

### 5.3 対策C: 1フレームのバイト数を減らす

#### C-1. 直前セルと同じ SGR を出さない

`render_halfblock`(`src/render.rs:38`)は全セルで前景・背景の SGR を無条件に発行し、
`render_braille`(`src/render.rs:55`)もインクのあるセルで毎回前景 SGR を発行している。
実測で 94×23 のフレームに含まれる SGR のうち、直前と同じ値のものは

| モード | フレーム | SGR個数 | うち直前と同一 | 削減見込み |
|---|---|---|---|---|
| halfblock | 85,642 B | 4,143 | 1,046 | 19,826 B(**23.1%**) |
| braille | 34,138 B | 1,477 | 227 | 4,301 B(**12.6%**) |

見た目は完全に同じまま halfblock が 23% 安くなる。行またぎで `\x1b[0m` を出しているので、
状態の持ち越しは行内に閉じて実装する(行頭で必ずリセットしてから比較を始める)。

#### C-2. web では braille を勧める / 既定を見直す

§2.2 と §3.1 のとおり、braille は halfblock に対してバイトが 40%・粒度が半分。
どちらの軸でも有利で、失うのは色の階調(前景色のみ・背景なし)だけ。

web 版の起動時に既定を braille にするか、少なくとも起動直後の案内で勧める。
`scripts/serve-web.sh` は `"$BIN" "$@"` で引数をそのまま渡すので、
`scripts/serve-web.sh --braille` で切り替えられる。既定を変えるかは体感の好みなので、
実装前にユーザーへ確認する。

#### C-3. 実画像モードの移動中解像度

`image_settle_low_res`(既定 true)が移動中に `delta=0` へ落とすため、実画像モードは
動いている間だけ halfblock と同じ粒度になる(`src/ui.rs:680,687`)。落とし方を
「1段だけ下げる」(high→mid、mid→mid)に変えるか、web では既定 false にする。

ただし実画像は PNG エンコードでコマ数が 7/秒まで落ちる(§2.2)ので、解像度を上げると
さらに遅くなる。実画像モードは「静止して見る用」と位置づけ、ドラッグの滑らかさは
AA モード側で解くのが素直。ここは変更しない案も含めて実機で判断する。

### 5.4 対策D: ブラウザ側の背圧と rAF 駆動

**やること**: overlay 側で、xterm.js が処理し切れていないバイト数を見て送信を止める。

```js
// term.write を包んで未処理バイト数を数える
var origWrite = term.write.bind(term);
var outstanding = 0;
term.write = function (data, cb) {
  var n = data.length;
  outstanding += n;
  return origWrite(data, function () { outstanding -= n; if (cb) cb(); });
};
```

`flushPan` は `outstanding` が閾値(1フレーム分の目安バイト数×2 程度)を超えている間は送らず、
`panPending` へ溜めたままにする。溜めた分は失われないので 1:1 は維持され、コマだけが落ちる。

あわせて次を変える。

| 項目 | 現状 | 変更後 |
|---|---|---|
| フラッシュ契機 | `setTimeout` 33ms 固定 | `requestAnimationFrame`。1フレーム1回、表示と位相が揃う |
| `terminalViewportSize()` | フラッシュのたびに `getBoundingClientRect()` | 起動時と `resize`/`orientationchange` でのみ再取得しキャッシュ |
| 慣性 | `setTimeout` 60ms | `requestAnimationFrame` + 経過時間ベースの減衰 |

**効果**: ブラウザが遅れているときに送信そのものを止めるので、「指を離した後も動き続ける」
状態を構造的に防げる。閾値の値は実機で詰める。

**リスク**: ttyd 同梱の xterm.js が `write(data, callback)` の callback を持つことが前提。
持たない版なら包み込みを外して、代わりに「送ってから次を送るまでの最小間隔を実測フレーム時間へ
自動追従させる」方式へ倒す。実機で先に確認する。

### 5.5 対策E: braille + 実画像のゲイン2倍を直す

`src/ui.rs:1452` で `dragmode::Layout` に渡す `ow`/`oh` を、実際に描画へ使った解像度から作る。

```rust
// 実画像モードでは rw/rh は zoom rz の解像度。zoom z 換算へ戻して渡す
let (pan_ow, pan_oh) = if img_inline { (rw / scale, rh / scale) } else { (ow, oh) };
let lay = dragmode::Layout { cols, rows: tr as u32, map_cols, map_rows, ow: pan_ow, oh: pan_oh };
```

`rw/scale = map_cols`・`rh/scale = map_rows*2` なので、実画像モードでは `opts.braille` の
値にかかわらず正しい 1:1 になる。`src/dragmode.rs` 側は変更不要。

テストは `pan_ratio_to_px` の純関数テストに「実画像モード相当の Layout」を1件足すだけでよい。
実機での確認は §2.5 と同じ手順(ステータス行の座標を読む)で数値化できる。

### 5.6 対策F: 開始の飛びと慣性

- **開始の飛び**: `passedTapSlop`(`web/touch-overlay.js:790`)がスロップを超えたと判定した時点で、
  `panLast` を現在の指の位置へ進めてスロップ分を送らない。指と地図の間に 12px の固定ずれが
  残るが、一般的な地図アプリと同じ挙動で、開始時の飛びは消える。
  現在のコメントは「溜まった分がまとめて流れる(移動量は失われない)」と書いてあり意図的だが、
  滑らかさを優先するなら捨てる側が正しい。
- **慣性**: rAF 化(§5.4)にあわせて、減衰を tick 回数ベースから経過時間ベース
  (`v *= pow(decay, dt/16.7)`)へ変える。フレーム落ちしても減速カーブが変わらなくなる。

## 6. 却下・保留した案

| 案 | 内容 | 判定 |
|---|---|---|
| CSS transform による先行スクロール | 未反映のパン量ぶん `.xterm-screen` を `translate` して 60fps で指に追従させ、termmap のフレームが来たら戻す。termmap 側は適用済み累計を OSC で返す | **保留**。指への追従は完璧になるが、左袖・ステータス行・端の帯まで一緒に動くので見た目が壊れる。地図領域だけを切り出す手段が DOM 側に無い。滑らかさが対策A〜D で足りなければ再検討する |
| 縦方向を端末のスクロール機能で送る | DECSTBM + 行スクロールで、縦パンのときだけ行の使い回しをする | 却下。横パンには使えず、斜めでは効かない。縦だけ速くなると方向で挙動が変わってかえって不自然 |
| 差分描画(前フレームと違うセルだけ書く) | 直前に書いたセル内容を保持し、変わったセルにだけカーソルを移して書く | 却下。パンではほぼ全セルが変わるので効かない。左袖とステータス行にしか効果が無く、その分は元々小さい |
| 256色化 | truecolor をやめて `\x1b[38;5;Nm` にする | 却下。SGR は約半分になるが色が明確に落ちる。同じバイト削減なら C-1(見た目不変)と C-2 を先にやる |
| 送信レートを上げる(60Hz) | `PAN_MIN_INTERVAL_MS` を 16 にする | 却下。§2.4 のとおりコマ数はブラウザ側で決まっており、送る量を増やしても詰まりが増えるだけ |
| ゲインに係数を掛ける | 見た目の速さを調整する | 却下。1:1 は #87 で意図して作った性質で、滑らかさの問題とは別。ここを触ると原因が混ざる |

## 9. テスト方針

Rust 側(`cargo test`):

- サブピクセル切り出し: 小数部 0.0 のとき従来の整数切り出しと一致すること / 小数部 0.5 で
  隣接ピクセルの中間色になること / 端(タイル境界・世界の端)で範囲外参照しないこと。
- `map_sig` の丸め: 同じ丸め値になる2つの中心座標で `need_build` が立たないこと /
  丸め値が1段変わったら立つこと。純関数へ切り出してテストする。
- SGR 重複除去: 同じ色が連続する画像で出力が短くなり、かつ ANSI を解釈した結果の
  セル色列が除去前と一致すること(見た目が変わっていないことの確認)。
- `pan_ratio_to_px`: 実画像モード相当の Layout(`ow=map_cols`, `oh=map_rows*2`)で 1:1 になること。
  braille フラグが立っていても実画像モードでは 2 倍にならないこと。
- 既存の `src/dragmode.rs` のテストはそのまま通ること。

計測の常設化:

§2 で使った PTY 計測を `tests/` 配下の統合テスト、または `scripts/` の計測スクリプトとして
リポジトリへ入れる。「1フレームのバイト数」「サブピクセル移動で再送が起きないこと」は
回帰しやすいので、数値の上限を持つテストにしておく。ネットワークに依存しないよう、
タイル未取得(グレー)の状態で測る。

ブラウザ側(自動テスト無し・実機手順):

1. §10 の計測窓で `dragModeSeen` が true であることを確認する(false なら #87 が効いていない)。
2. 斜め45度にゆっくりドラッグして、地図が階段状に振れないこと。
3. 速いスワイプで指を離した後、地図が動き続けずに慣性だけで自然に止まること。
4. ドラッグ開始時に地図が飛ばないこと。
5. braille と halfblock を切り替えて体感差を比べる。
6. 実画像モードと braille を同時に有効にして、指と地図の移動量が一致すること(対策E の確認)。
7. PC の Chrome でマウスドラッグと物理キーボードの矢印が従来どおり動くこと。

## 10. 実機で測る手順

iPhone 上で何が起きているかは、手元では測れない。overlay に計測窓を足して現物で数字を取る。

`window.__termmapTouch` へ次を追加する(既存の `getDragAxes` / `setDragAxes` と同じ扱い)。

```js
stats: function () {
  return {
    dragModeSeen: dragModeSeen,          // false なら #87 が効いていない
    dragAxes: dragAxes,
    outstandingBytes: outstanding,       // xterm.js が処理し切れていない量
    bytesPerSec: <直近1秒に term.write へ来たバイト数>,
    framesPerSec: <直近1秒に届いた地図フレーム数>,
    panSentPerSec: <直近1秒に送った PAN の回数>,
    cellSize: { w: <cellWidth>, h: <cellHeight> },  // §3.1 の CSS px 換算の実測値
    viewport: terminalViewportSize()
  };
}
```

フレーム数の数え方は、termmap 側がフレーム末に軽いマーカー(既存の OSC 9997 と同じ枠組みで
1バイトぶんの通知)を出すのが確実。追加コストは1フレームあたり十数バイトで、
§2.2 のフレームサイズに対して無視できる。

Safari の開発者ツール(Mac と USB 接続)から `__termmapTouch.stats()` を叩いて、
スワイプ中の `framesPerSec` と `bytesPerSec` を読む。ここが §2.4 のどの行に当たるかで、
対策C のどこまでやるかが決まる。
