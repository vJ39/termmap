データ取得側(NIEDの集計クエリ・1次メッシュ+年代の複合キー・fresh 30日・`B`キーの2段目)は
変えない。変えるのは表示だけ。

## 0. 先に置く事実

設計を左右する事実を先に置く。いずれもこの文書を書く時点で実際にコードを読み・APIを叩いて確認した。

### 0.1 端末の1画面は「市区町村を並べて見比べる」には狭い(最重要)

コロプレスは普通「複数の区画を色で見比べる」ために使う。termmap でそれが成り立つかを先に確かめた。

画面が覆う地理的な幅は `地図領域の画素幅 × meters_per_pixel(lat, z)` で決まる。
`meters_per_pixel` は `src/geo.rs` の実装そのままで、北緯35度なら `128,232 / 2^z` m。
画素幅は描画モードで変わる(`src/ui.rs` の `ow`/`rw`)。

| モード | 画素幅 | 備考 |
|---|---|---|
| ハーフブロック(既定) | `map_cols` | 1セル=横1px |
| braille / edge | `map_cols × 2` | 1セル=横2px。同じ z でも倍の範囲が写る |
| 実画像(iTerm2) | `map_cols × scale` かつ `z+Δ` | 解像度と z が同時に上がるのでハーフブロックと同じ地理範囲 |

地図領域120桁のときの画面幅(北緯35度):

| z | m/px | ハーフブロック・実画像 | braille |
|---|---|---|---|
| z9 | 250 | 30.1 km | 60.1 km |
| z10 | 125 | 15.0 km | 30.1 km |
| **z11**(レイヤ下限) | 62.6 | **7.5 km** | **15.0 km** |
| z12 | 31.3 | 3.8 km | 7.5 km |
| z13 | 15.7 | 1.9 km | 3.8 km |
| z14 | 7.8 | 0.9 km | 1.9 km |

実際に境界データ(§2)へ当てて、東京駅中心の画面に何区域が掛かるかを数えた。

| 状態 | 画面幅 | 掛かる市区町村数(東京中心・実測) |
|---|---|---|
| z11・ハーフブロック | 7.5 km | 9 |
| z11・braille | 15.0 km | 21 |
| z9・ハーフブロック | 30.1 km | 37 |
| z9・braille | 60.1 km | 96 |

**都市部なら z11 でも9〜21区域が入り、コロプレスとして成立する。** 一方、地方は市区町村が
10〜30km四方あるので、同じ z11 で1〜2区域にしかならない。つまり見え方が土地によって
大きく変わる。ここから2つ決まる。

1. **地方では「複数を見比べる図」ではなく「いま見ている土地がどれだけ記録を積んでいるか」に
   なり、塗りが画面の大半を覆う。** これは欠陥ではなく、重ねるハザードマップを市街地まで
   拡大したときと同じ見え方である。逆に言えば **塗りは地図を潰さない濃さでなければ
   使い物にならない**(§3.2・§4.2)。
2. **地方でも見比べる読み方を出すには z9〜z10 が要る。** そこは現在の取得方式が禁じている
   (下限 z11)。禁じている理由は取得側の都合であってデータの都合ではないので、外せる。
   §5.4 に別ステージとして切り出す。

### 0.2 半透明合成と点描間引きは既に入っている(雨雲レーダーの経路)

#79(気象警報)の設計書には「`OverlayLayer` は `ink: Vec<Option<[u8;3]>>` の二値マスクで
半透明合成の仕組みが無い」と書いてあるが、これは雨雲レーダーが入る前の記述で、**今は解消している**。
`src/render.rs` に次の2つがある。

| 関数 | 用途 | 効き方 |
|---|---|---|
| `blend_rgba_over(base: &mut RgbImage, layer: &RgbaImage, opacity: f64)` | 実画像・ハーフブロック・classify | source-over のアルファ合成。地図が下に透ける |
| `ink_radar_into_overlay(ov, layer, min_alpha, density)` | braille / edge | 4x4 Bayer で間引いて `OverlayLayer` へ不透明インクを置く |

呼ばれ方は `src/ui.rs` と `src/main.rs::render()` で3経路に分かれている。

| 経路 | 条件 | 合成場所 |
|---|---|---|
| 実画像 | `cfg.image_mode && image_capable()` | `ui.rs` で `blend_rgba_over(&mut img, ...)` してから `composite(ov)` |
| braille / edge | `!img_inline && (braille || edge)` | `RadarInk` を `build_overlay` へ渡し、最背面にインクを置く |
| ハーフブロック / classify | それ以外 | `main.rs::render()` の中。classify は **`recolor()` の後** に合成する(先に混ぜると淡い青が湖に化ける) |

**コロプレスはこの経路に「雨雲より1枚後ろ」の層として乗せる。** 新しい合成の仕組みは要らない。
ユーザーの「雨雲レーダーみたいに色付けしてほしい」は、文字通り雨雲と同じ機構で実現できる。

ただし `render()` も `build_overlay()` も **RGBA層を1枚しか受け取らない**ので、そこは
複数枚を受ける形へ広げる(§5.3)。

### 0.3 NIEDのサービスが持つポリゴンは都道府県だけ

`https://agis.bosai.go.jp/webgis/rest/services/dil-db/saigai/MapServer?f=json` を実際に叩いた結果:

| id | 名前 | 種別 |
|---|---|---|
| 0 | 災害事例 | `esriGeometryPoint` |
| 1 | 都道府県 | `esriGeometryPolygon` |
| 2 | `syukei` | テーブル(`PREF_CODE`/`SAIGAI_YEAR`/種別ごとの件数) |

**市区町村の境界は無い。** 都道府県ポリゴンは持っているが、§0.1 のとおり画面幅が最大でも
60km なので都道府県で塗ると常に全画面が1色になり、情報量がゼロになる。`syukei` テーブルも
集計単位が都道府県なので同じ理由で使えない。

→ **市区町村境界は外部から持ってくるしかない**(§2)。

### 0.4 集計行に市区町村コードを、行数を増やさずに載せられる

レイヤ0のフィールドは292個あり、その中に `CHIDAN_CODE`(エイリアス「地方公共団体コード」・文字列)
がある。**実値は `"JP12208"` = `JP` + 全国地方公共団体コード5桁**(全1,635行が例外なく7文字。
6桁チェックデジット付きではない)。

現在の1段目クエリは `groupByFieldsForStatistics=fX,fY,SAIGAI_SYUBETSU_1` で市区町村コードを
取っていないが、**足しても行数が増えない**ことを実測した。

| グループ化キー | 行数 | サイズ | 打ち切り |
|---|---|---|---|
| `fX,fY,SAIGAI_SYUBETSU_1`(現行) | 236 | 25.0 KB | 無し |
| `CHIDAN_CODE,SAIGAI_SYUBETSU_1` | 236 | 17.8 KB | 無し |
| `fX,fY,CHIDAN_CODE,SAIGAI_SYUBETSU_1` | 236 | ― | 無し |

いずれも1次メッシュ5339。**座標118個に対して `CHIDAN_CODE` が複数ぶら下がる行は0件 = 1対1**
だったので、`CHIDAN_CODE` を足しても行が割れない。#75 が「年を足すと2,000行で打ち切られる」と
書いた事情(`docs/disaster-history-overlay-design.md` §2.3)は、市区町村コードには当てはまらない。

これで §1-3 の突合方式の選択が変わる(§1.1)。

なお **`resultOffset` は集計クエリでは黙って無視される**(offset を変えても同一レスポンスが返る)
ことも分かった。この機能ではページングしないので影響しないが、将来ページングを足すときに
「7ページ取れたつもりで中身が全部同じ」という二重計上事故になる。`docs/disaster-history-data-investigation.md`
へ注意として書き足す。

### 1.1 突合をコード結合にする理由

候補は2つある。

| 方式 | やり方 | 判定 |
|---|---|---|
| A. **コード結合** | 1段目の `groupByFieldsForStatistics` に `CHIDAN_CODE` を足し、境界データの市区町村コードと突き合わせる | **採用** |
| B. 代表点の内外判定 | 既に持っている `DisasterSite.lat/lon` が、どの境界ポリゴンの中にあるかを判定する | 却下(ただし別用途で残す) |

当初はBを採るつもりだった(取得側に手を入れずに済むため)が、§0.4 の実測で前提が崩れた。

- **行数が増えない。** Bを推した最大の理由は「グループ化キーを増やすと2,000行の打ち切りに
  近づく」だったが、実測で 236行 → 236行、打ち切り無し、座標と1対1。この理由は消えた。
- **境界の簡略化に影響されない。** 境界データはJMA側で簡略化されている(§2)ので、
  実際の市境から数十m動いている。代表点が境界近くにある市区町村では、隣の市区町村へ
  誤って割り当たりうる。コード結合ならこの誤差が原理的に効かない。
- **飛地・離島で外れない。** Bは代表点がポリゴンの外に落ちると塗れない。
  1次メッシュ5339の118地点では1件も外れなかった(§2.3)が、全国で0件である保証は無い。

Aの代償は `DisasterSite` にフィールドが1つ増えることで、既存のディスクキャッシュが
`plotcache::load` の `serde_json::from_str(..).ok()?` で読めなくなり、全セルが1回取り直しになる。
取り直しは自己修復するので、壊れ方は「アップグレード直後の初回だけ通信が要る」で収まる。
`#[serde(default)]` で古いキャッシュを読めるようにはしない
(コードが空のセルは塗れず、原因の分からない虫食いになるため。取り直させた方が素直)。

**内外判定は捨てない。** ステータス行に「いまいる市区町村」を出す(§4.3)には、中心十字が
どのポリゴンの中かを判定する必要がある。#79(気象警報)も class10s に対して同じ判定を要する。
`src/geopoly.rs` はそのために置く(§5.2)。

## 2. 市区町村境界データ

**気象庁の `class20s` 境界GeoJSON(10ファイル分割)を、実行時に取得してディスクへ永続キャッシュする。**
以下はすべて実際に取得して数えた値(2026/08/17)。

### 2.1 実測

| URL | 内容 |
|---|---|
| `https://www.jma.go.jp/bosai/common/const/geojson/class20s_{0..9}.json` | 区域ポリゴン。10ファイル |
| `https://www.jma.go.jp/bosai/common/const/relm.json` | 10要素の配列。`[i]` が `class20s_{i}.json` の外接矩形(`{"ne":[lat,lon],"sw":[lat,lon]}`) |
| `https://www.jma.go.jp/bosai/common/const/area.json` | `class20s` に1,805件の `name`/`kana`/`parent`(境界が要らない用途向け。今回は使わない) |

| 項目 | 実測値 |
|---|---|
| ファイル数 / 合計 | 10ファイル / 2.98 MB |
| 1ファイルのサイズ | 49 KB(`_9`)〜397 KB(`_0`) |
| 区域数 | 1,806 |
| **総頂点数** | **148,424(1区域あたり平均82頂点)** |
| 幾何の型 | 全件 `MultiPolygon`(離島・穴を型で区別せず持てる) |
| 座標の桁 | 小数4桁(緯度で約11m) |
| `properties` | `code`(7桁文字列)/ `name`(和名)/ `enName` / `labelPoints` |

`class20s_0.json` の1件目の実物:

```json
{"code":"0110000","name":"札幌市","enName":"Sapporo City","labelPoints":[[141.2505,42.9907]]}
```

**JMA側で既に簡略化されている**(座標が小数4桁、1区域82頂点)。塗りを出す最も細かいズーム
z13 は 15.7 m/px なので、11mの座標粒度は1画素未満に収まる。**こちらで簡略化する処理は要らない。**

### 2.2 コード体系: 先頭5桁が全国地方公共団体コード

| `code` | `name` | 全国地方公共団体コード |
|---|---|---|
| `0110000` | 札幌市 | 01100 |
| `1310100` | 千代田区 | 13101 |
| `2710000` | 大阪市 | 27100 |
| `1220800` | 野田市 | 12208 |

1,806区域は **1,757個の5桁コード** に対応する。内訳は次のとおり。

- 1,716区域は末尾が `00` = 市区町村まるごと
- 90区域は末尾が `00` 以外 = **40市区町村が複数の区域に分かれている**
  (例 `0120601`釧路市釧路 / `0120602`釧路市阿寒 / `0120603`釧路市音別、横浜市の南部・北部・西部)

**件数の割り当ては先頭5桁で行い、ポリゴンは7桁のまま扱う。** 理由は §2.4 の実測にある。

### 2.3 2つのデータが地理的に整合していることの確認

コードで結合する以上、コードが同じものが同じ場所を指していなければ意味がない。
1次メッシュ5339(東京〜千葉西部)の集計を実際に取り、118地点すべてを内外判定に掛けた。

```
1次メッシュ5339 の地点数: 118
ポリゴン内に落ちた: 118/118  外れた: 0
塗られる市区町村数: 118   (5桁コードの重複なし = 代表点は市区町村あたり1つ)
```

| 点 | 判定結果 |
|---|---|
| `139.874828, 35.955106`(#75の設計書に出てくる代表点) | `1220800` 野田市 |
| 東京都庁 | `1310400` 新宿区 |
| 大阪市役所 | `2710000` 大阪市 |
| 海上 `140.5, 35.0` | どの区域にも入らない(正しく外れる) |

**代表点は市区町村あたりちょうど1つ**で、政令指定都市も市まるごとで1点だった
(横浜市に166件が1点として入っている)。区ごとには分かれていない。

形状そのものの精度も、香川県で国土数値情報(N03)と突き合わせた結果、
**17市区町村すべてが面積比98.5〜101.0%・県計100.13%** で一致した。
「気象庁の警報区分だから行政界と違うのでは」という懸念は、色塗り用途では問題にならない。

### 2.4 5桁への丸め方(横浜市型と広島市型)

JMAの7桁コードとNIEDの5桁コードを突き合わせるには丸めが要る。丸め方は2種類ある。

**横浜市型(下2桁が細分)** — 素直に `code[..5]` を取れば済む。

| JMA | 5桁 | NIED |
|---|---|---|
| `1410011` 横浜市北部 / `1410012` 横浜市南部 | `14100` | `JP14100` ✓ |
| `0120601` 釧路市釧路 / `0120602` 阿寒 / `0120603` 音別 | `01206` | `JP01206` ✓ |

こうして分割されているのは **40市区町村**(仙台・横浜・相模原・静岡・浜松・釧路 等)。

**広島市型(区が別コード)** — `code[..5]` では合わない。

| JMA | `code[..5]` | NIED | 結果 |
|---|---|---|---|
| `3410100` 広島市中区 〜 `3410800` 佐伯区(8区) | `34101`〜`34108` | `JP34100`(278件) | ✗ 合わない |
| `2810100` 神戸市東灘区 〜 `2811100` 西区(9区) | `28101`〜`28111` | `JP28100`(137件) | ✗ 合わない |

政令指定都市20市のうち、**区単位で持たれているのは広島市と神戸市だけ**(実測で全20市を確認。
他は市まるごと、または横浜市型の細分)。NIED側は両市とも市単位のコード1つしか持たない
(`JP34100` 278件 / `JP28100` 137件 を実クエリで確認)。

放置すると全国63,849件のうち **415件(0.65%)が塗られない**。対策は
**17行の対応表(広島市8区・神戸市9区 → `34100`/`28100`)** を `src/muni.rs` に置くこと。
これで一致率は 63,848/63,849 になる(残る1件は那珂川市で、NIED側が2018年の市制施行前の
旧コード `40305` のまま。データ提供元の問題なので追わない)。

**ポリゴンは7桁のまま扱う。** 5桁へ統合(リングを連結)すると、統合した区域どうしの
内部境界まで縁取りが引いてしまう。割り当ては5桁・描画は7桁にすれば、横浜市の2区域が
同じ色で塗られたうえで区域ごとの縁取りが残る(内部に細い線が1本入るだけで色は連続する)。

### 2.5 パースで踏む落とし穴(実測)

- **`code` が数値とは限らない。** `"hoppo"`(根室地方)が1件混入している。
  **コードを整数としてパースすると落ちる。** 文字列のまま扱い、`code[..5]` も
  バイト長を確認してから切る。
- **リングの巻き方向が不統一**(CW 2,936 / CCW 65)。向きに依存する塗り方
  (nonzero winding)は使えない。§3.1 で even-odd を選んでいるのはこのため。
- **`class20s_0.json` が北海道。** 0始まりの10ファイルで、`_0` を取りこぼすと
  道内179市町村が丸ごと欠ける。`relm` の矩形で選べば自動的に当たるが、番号を
  1始まりと勘違いしないこと。
- ホールは0件・全リング閉合。ただし even-odd で塗るのでどちらでも壊れない。

### 2.6 他の候補を落とした理由

境界データの候補は実際に取得して測った。判定の軸はサイズだけではなく、
**NIEDの件数がどれだけ載るか**(政令市の扱いが食い違うと件数を丸ごと取りこぼす)。

| 候補 | サイズ | 形式 | NIED件数の一致 | 判定 |
|---|---|---|---|---|
| **気象庁 class20s** | 2.98MB(10分割・1枚49〜397KB) | GeoJSON | 99.35% → **17行の表で 63,848/63,849** | **採用** |
| smartnews `designated_city` | 542KB | TopoJSON | 63,848/63,849 | 次点 |
| K-Oxon `ja_municipality_area_5` | 1.27MB | GeoJSON | 63,848/63,849 | 次点 |
| smartnews 標準(区単位) | 580KB | TopoJSON | 61,919/63,849 (**97.0%**) | 却下 |
| geoshape `jp_city`(区単位) | 2.48MB | GeoJSON | 62,016/63,849 (97.1%) | 却下 |
| 国土数値情報 N03 | **展開553MB・約1,600万頂点** | Shapefile/GeoJSON の zip | ― | 却下 |
| 地球地図日本 / Natural Earth / dataofjapan | ― | ― | ― | 却下 |

**区単位のデータは政令市の件数を丸ごと落とす。** NIEDが政令市を市単位コードで持つため、
区単位の境界だと広島市278件・横浜市172件・静岡市160件…で計1,930件(3.0%)が宙に浮く。
市単位へ丸めてあるデータでないと使えない。

**N03そのものは不適。** 全国で約1,600万頂点・GeoJSON展開553MB。ターミナル描画に要る精度の
3桁上にある。自前で Douglas-Peucker を掛けても、eps=0.001度(≈111m)まで潰して香川県で
2,855頂点までしか落ちず、しかも736リング中648(離島)が消滅した。簡略化パイプラインは
引き合わない。加えて zip展開とShapefileパーサで **新規crateが2つ要る**——
`Cargo.toml` は8個で、base64もURLエンコードも自前で書いてきたこの repo の方針に反する。

**地球地図日本は名称がローマ字のみ**(ステータス行に和名を出せない)、
**Natural Earth と dataofjapan は都道府県止まり**(47件)で、いずれも市区町村を塗れない。

**smartnews / K-Oxon を次点に留める理由。** 件数一致は class20s + 17行の表と同じ
63,848/63,849 で、smartnews は542KBと小さい。それでも第一候補にしないのは3点。

1. **TopoJSON はアーク復号が要る。** 量子化されたデルタ列・負のアーク番号による反転・
   オブジェクトからアークへの参照解決を書くことになる。GeoJSON なら `serde_json` で
   数十行で済む。
2. **生成物をコミットすることになる。** この repo は生成物をコミットしない方針を既に
   持っている(`.gitignore` の `/web/index.html` = 約730KBの生成物、
   「リポジトリには入れず手元で生成する」)。`raw.githubusercontent.com` から実行時に
   取りに行くのは、第三者リポジトリに依存する点で気象庁より弱い。
3. **smartnews は N03-2021 ベースで境界が5年古い。** class20s は
   `last-modified: 2026-08-12`。

TopoJSON の復号を別の理由で書くことになったら、smartnews は再検討に値する。

### 2.7 持ち方: 同梱ではなく実行時取得+永続キャッシュ

| 案 | 判定 |
|---|---|
| A. `include_bytes!` でビルド時同梱 | 却下 |
| B. **実行時に取得してディスクへ永続キャッシュ** | **採用** |

Aを却下する理由。2.98MB を素のまま同梱するとバイナリが 5.5MB → 8.5MB になる。
1e-4グリッド量子化+デルタzigzag varint で符号化する試算では **451,800 B まで縮んだ**ので
サイズ自体は許容範囲に入るが、そのために符号化スクリプト・復号コード・生成物のコミットが要る。
しかも **この repo は生成物をコミットしない方針を既に持っている**
(`.gitignore` に `/web/index.html` = 約730KBの生成物、「リポジトリには入れず手元で生成する」)。

Bで失うのは「初回だけ通信が要る」ことだけで、**このレイヤは災害件数の取得自体が
通信を必要とする**(NIEDへ問い合わせる)。境界だけをオフラインで持っていても
塗るべき件数が無いので、可用性は実質変わらない。

さらにBは **既存の `PlotLayer<T>` にそのまま乗る**。

| 項目 | 値 |
|---|---|
| セル | `relm` の10領域 |
| キー | `c20s0` 〜 `c20s9`(`plotcache::valid_key` の英数字16文字以内に収まる) |
| 被覆関数 | 視野bboxと `relm[i]` の矩形が交差する `i` を全部返す |
| 取得関数 | `class20s_{i}.json` を取って `Vec<MuniArea>` へパース |
| fresh TTL | **180日**(区域定義は市町村合併等でごく稀にしか変わらない) |
| stale上限 | 無し(古くなっても捨てない。境界が誤りになることはない) |
| 最大エントリ数 / バイト数 | 10 / 10MB |
| ズーム下限 | 過去災害レイヤと同じ(Stage A は11、Stage B は9) |

`relm` の矩形は互いに重なっているが、各ファイルの中身の外接矩形なので
「視野に入る区域は必ず、視野と交差する矩形のファイルのどれかに入っている」。取りこぼさない。
実測では東京・札幌・大阪・那覇のいずれも該当ファイルは1枚で、期待する市区町村が入っていた。

`relm.json` 自体は10要素の小さな配列で内容が変わらないので、**取りに行かずソースへ定数として
書き写す**(10行のテーブル)。境界ファイルを1枚も取れない状態でも被覆計算だけは動く。

### 2.8 出典

`README.md` / `docs/MANUAL.md` / 設定ONの直後のメッセージに、既存の雨雲レーダーと同じ形で
出典を出す。過去災害レイヤは出典が2つになる。


## 3. 描画

### 3.1 ポリゴンのラスタライズ

`src/render.rs` にポリゴンを塗る関数が無いので新設する。既存の `draw_line`/`draw_ring`/
`draw_marker` と同じ「純粋な描画プリミティブ」として置き、どの市区町村を何色で塗るかは
呼び出し側(§5.2)の責務にする。

```rust
// 画面座標のリング列(外周+穴)を even-odd 規則で塗る。
// リングは閉じている必要はない(末尾と先頭を暗黙に結ぶ)。
// ポリゴンの外接矩形と画像の重なりだけを走査するので、画面外のポリゴンは即座に返る。
pub fn fill_rings_rgba(img: &mut RgbaImage, rings: &[Vec<(i32, i32)>], color: [u8; 4]);

// リングの輪郭(縁取り)。塗りより前面、雨雲より背面。
pub fn stroke_rings_rgba(img: &mut RgbaImage, rings: &[Vec<(i32, i32)>], color: [u8; 4], thickness: u32);
```

塗りはスキャンライン方式。走査線 `y` ごとに、全リングの辺との交点 `x` を集めて昇順に並べ、
1番目と2番目・3番目と4番目…の間を塗る(even-odd)。辺の採否は `(y0 <= y) != (y1 <= y)` の
半開区間規則にする。頂点をちょうど通る走査線で交点を二重に数えて塗りが裏返るのを防ぐため。

**even-odd を選ぶのは、穴(飛地に囲まれた区域・湖の中の境界)と多重ポリゴン(離島)を
1回の走査で同時に処理できるから。** 外周と穴を区別して持つ必要がなく、GeoJSON の
`Polygon`/`MultiPolygon` のリングを全部同じ配列に並べるだけで正しく塗れる。

計算量は「外接矩形の高さ × 辺の数」。**1区域あたり平均82頂点**(§2.1)なので、
画面に20区域あっても高さ800画素で 82×800×20 ≒ 130万回。しかもラスタライズは
地図を組み直すフレームでしか走らない(§3.3)。走査線ごとの辺テーブルのような
最適化は要らず、素直な実装のままにする。

### 3.2 3つの出力経路への乗せ方

コロプレスは画面サイズの `RgbaImage` を1枚作り、雨雲と同じ3経路へ流す。**雨雲より背面**に置く
(雨は今の話、災害履歴は土地の話なので、今の情報が上に来るのが正しい)。

| 経路 | 合成 | 濃さ |
|---|---|---|
| 実画像 / ハーフブロック / classify | `blend_rgba_over` を コロプレス → 雨雲 の順に呼ぶ | 既定 0.45 |
| braille / edge | **Bayer間引きではなく疎な点描**(下記)+ 縁取り | 間隔で表現 |

**braille/edge で Bayer 間引きをそのまま使ってはいけない。** `render_braille` は
「そのセル(2x4画素)にオーバーレイのインクが1つでもあれば、セル全体の文字色をインク色にする」
実装になっている(`else if ovn > 0` の分岐が地図側の色を捨てる)。

`BAYER4` は4x4周期なので、braille の1セル(横2×縦4画素)はそのタイルのちょうど半分を覆う。
薄い側の density=0.35(閾値5.6)で数えると、セルに入る8つの閾値は
`x%4∈{0,1}` なら `{0,8,12,4,3,11,15,7}` で 5.6未満が3つ、`x%4∈{2,3}` なら
`{2,10,14,6,1,9,13,5}` で3つ。**どの位相でも必ず3画素にインクが乗る = 全セルが塗り色に化ける。**
雨雲は降っている場所だけなので実害が無いが、コロプレスは画面全体を覆うため
**braille の線画が丸ごと単色になる**。

そこで面塗り専用の間引きを別に用意する。

```rust
// 大きな面を braille/edge へ乗せるための疎な点描。spacing 画素ごとに1点だけ置く。
// Bayer(4x4周期)と違い周期を大きく取れるので、braille のセル(2x4画素)の大半を
// 塗り色に化けさせずに「色の粒が撒かれている」状態にできる。
pub fn stipple_rgba_into_overlay(ov: &mut OverlayLayer, layer: &RgbaImage, spacing: u32);
```

`spacing=8` なら 8x8=64画素に1点、braille セル8個に1点なので、色が付くセルは約12%に収まる。
濃さ設定は間隔で表す(薄い=16 / 標準=8 / 濃い=4)。

縁取りは braille/edge でも `OverlayLayer` へ普通に線として置く(線画モードとは相性が良い)。

### 3.3 ラスタライズのタイミング

毎フレームは作らない。`ui.rs` は既に `map_sig`(中心・ズーム・各レイヤの `generation()` 等の
ハッシュ)が変わったときだけ地図を組み直す仕組みを持っているので、コロプレスもそこに乗せる。
`map_sig` に足すのは次の3つ。

- 過去災害レイヤの `generation()`(既に入っている)
- コロプレスのON/OFFと濃さ設定
- 描画ズーム `rz`(既に `cx/cy/z` として入っている)

結果として、パンもズームもしていないフレームではラスタライズが1回も走らない。

### 3.4 マーカーとの役割分担

代表点マーカーを消さない。消すと `B`(その地点の事例一覧)が何を指すのか画面から分からなくなる。
ただし件数を伝える役目は塗りへ移るので、外周リングは塗りが出ているズームでは出さない。

| ズーム | 塗り | 縁取り | 中心の小さな塊 | 件数リング |
|---|---|---|---|---|
| z10以下 | ― (レイヤ自体が取得しない) | ― | ― | ― |
| z11〜z13 | 出す | 出す | 出す | 出さない(塗りが担う) |
| z14 | 出さない(1市区町村で画面が埋まる) | 出す | 出す | 出す |
| z15以上 | 出さない | 出さない(簡略化のずれが見えるため) | 出す | 出す |

z14以上で塗りをやめるのは、画面幅が1km前後になり(§0.1)、塗りが「全面が同じ色」に
退化して情報を持たなくなるため。そのズーム帯では従来のマーカー表示がそのまま正しい。

## 4. 色分け

### 4.1 軸: 種別の色 × 件数の濃さ

| 案 | 見え方 | 判定 |
|---|---|---|
| (i) 件数だけの逐次配色(1色相の濃淡) | 多い/少ないだけが読める | 却下 |
| (ii) **最多種別の色 × 件数のアルファ** | 多い/少ない と 何の災害か が同時に読める | **採用** |

(ii) を採る理由は、**現在のマーカーが持っている情報(色=最多種別・大きさ=件数)を1つも
落とさずに、点から面へ移せる**から。置き換えで情報が減らない。

「色相と濃さの2軸は市区町村間の比較を難しくする」という一般論はそのとおりだが、
このデータは9割近くが風水害(#75 §2.4 の実測)なので、実際には画面のほぼ全部が
青系の濃淡になり、事実上 (i) と同じ読み方になる。色相が変わるのは地震・雪氷が
上回っている土地だけで、そこが目立つのは望ましい挙動。

色は `DisasterKind::color()` をそのまま使う(既にマーカーで使っている値を再利用する。
塗りとマーカーで色が食い違わない)。

### 4.2 濃さの段階

`src/disaster.rs` に `marker_radius` と並べて置く。

```rust
/// 塗りのアルファ(件数5段)。実測(1地点あたり中央値18件・最大166件)に合わせて刻む。
/// この値に濃さ設定(0.30/0.45/0.60)が掛かる。
pub fn fill_alpha(total: u32) -> u8 {
    match total {
        0..=4 => 70,
        5..=14 => 120,
        15..=39 => 170,
        40..=99 => 215,
        _ => 255,
    }
}
```

**段階は固定値で、画面内の分布に合わせた相対配色(分位数)にはしない。** 相対にすると、
同じ市区町村がパンするたびに色を変える。「濃い=記録が多い」が場所によって別の意味に
なってしまい、ハザードマップとして読めなくなる。

濃さ設定の既定を 0.45 にするのは、雨雲(既定 0.55)より弱くする必要があるため。
雨雲は降っている場所だけを覆うが、コロプレスは常に画面の大半を覆うので、同じ濃さだと
地図が読めなくなる(§0.1)。

### 4.3 凡例の代わりにステータス行を使う

ステータス行に凡例を置く幅は無い。代わりに **中心十字がいる市区町村そのものを出す**。
これは凡例より直接的で、ツーリング中に知りたいこと(いまどの町にいて、その町に
どれだけ記録があるか)にそのまま答える。

| 状態 | 現在 | 変更後 |
|---|---|---|
| 中心が塗られた市区町村の中 | `🌊12地点(B) ` | `🌊野田市 89件(B) ` |
| 中心がどの市区町村にも入らない/記録が無い | `🌊12地点(B) ` | `🌊12地点(B) `(現状のまま) |
| 取得中・広域・記録無し・stale | 現状のまま | 現状のまま |

市区町村名は境界データ側が持っているものを使う(§2)。件数はその市区町村へ紐づいた
`DisasterSite.total()`。

```rust
// src/choropleth.rs
pub struct Shading { pub opacity: f64, pub fill: bool, pub outline: bool }

/// 表示中の市区町村を災害件数で塗った層を1枚作る。塗る対象が無ければ None。
pub fn build_layer(

    cx: f64, cy: f64, z: u32, w: u32, h: u32, sh: Shading,

/// 5桁コード → (件数, 最多種別)。build_layer と area_summary が共有する純関数。
pub fn tally(sites: &[&disaster::DisasterSite], areas: &[&muni::MuniArea])
    -> HashMap<String, (u32, disaster::DisasterKind)>;

/// 中心十字がいる市区町村の名前と件数(ステータス行 §4.3 用)。
pub fn area_summary(sites: &[&disaster::DisasterSite], areas: &[&muni::MuniArea], lat: f64, lon: f64)
    -> Option<(String, u32)>;
```

`build_layer` の中身。

1. `tally`: 各 `DisasterSite` の `muni_code` をキーに件数と最多種別を積む。
   同じコードに複数の地点が落ちた場合は件数を足し、種別は件数の多い方を採る
   (実測では市区町村あたり代表点は1つだが、重複しても壊れない形にしておく)
2. 視野bboxに掛かる区域を `MuniArea.bbox` で粗く絞る
3. 絞った区域のうち `MuniArea::muni_code()` が集計表に載っているものだけ、
   種別色 × `fill_alpha` で `fill_rings_rgba`
4. `stroke_rings_rgba` で縁取り

`area_summary` だけが `geopoly::point_in_rings` を使う(中心十字がどの区域の中かを判定し、
その区域の `name` と、`muni_code()` で引いた件数を返す)。

境界データの取得段取りは既存の枠組みに乗せるだけで、新しい仕組みを作らない。

### 5.3 `src/ui.rs` と `src/main.rs`(RGBA層を複数枚受ける)

### 5.4 ズーム下限を下げる(別ステージ・Stage B)

§0.1 のとおり、コロプレスが「見比べる図」になるのは z9〜z10 で、そこは現在取得しない。
理由はデータではなく `plotlayer.rs` の被覆計算にある。

`PlotLayer::tick` は `view_bbox(cx, cy, z)` を使い、`VIEW_HALF_PX = 900` の固定半径で
視野を見積もる。**実際の描画は120桁なら横120〜240画素しかない**ので、z が浅くなるほど
900画素の見積りは実態から離れ、z9 では 1800px × 250m = 451km 四方を覆う計算になって
1次メッシュが30枚を超え、`MAX_CELLS_PER_JOB = 9` に掛かって取得が止まる。

実際の描画画素数を使えば z9 でも収まる。braille・160桁なら 320×180画素 = 80km × 45km で、
余白を1.5倍見ても 120km × 68km = 1次メッシュ2〜6枚。

変更は次の2点に収まる。

- `PlotLayer` に `view_half_px`(既定900)を持たせ、`tick` の被覆計算だけがそれを使う
- 過去災害レイヤだけ実描画寸法から算出した値を渡し、`min_zoom` を 11 → 9 へ下げる

`items(view)` は呼び出し側からbboxを受けるままにする(`B` キーが「中心に一番近い地点」を
探す範囲を狭めないため)。他の4レイヤは既定900のままで挙動が変わらない。

これは取得の挙動を変えるので、コロプレス本体(Stage A)とは別コミットにする。

## 8. テスト方針

ネットワークに触れない部分を全部単体テストにする(既存モジュールと同じ)。

- `geopoly::point_in_rings`: 単純な矩形 / 凹多角形 / 穴あり(外周+内周)/ 多重ポリゴン(離島)/
  境界線上の点 / 頂点をちょうど通る走査線 / 空リング(panicしない)
- `muni::parse_areas`: 実応答の抜粋から `code`/`name`/リング/bbox を読む /
  `MultiPolygon` の全リングが平らに並ぶ / `geometry` 欠損・座標欠損の行を捨てる /
  壊れたJSON・`features` 無しで空 `Vec`(panicしない)
- `muni::relm_indices`: 東京(=3)・札幌(=0)・大阪(=5)・那覇(=9)が実測どおりの番号を返す /
  日本の外は空 / 矩形が重なる位置では複数返す
- `muni::MuniArea::muni_code`: 7桁 → 先頭5桁 / **広島市8区・神戸市9区が `34100`/`28100` へ丸まる** /
  横浜市の `1410011`・`1410012` が `14100` になる / `"hoppo"` のような非数値・短いコードで
  panicしない(整数パースしない)
- `WARD_TO_CITY` の網羅性: 表の17件が実際の広島市・神戸市の区コードと一致し、重複が無い
- `plotcache`/`plotlayer`: `MuniArea` がディスクを往復できること
  (`all_five_real_item_types_survive_a_trip_through_the_disk_cache` に6つ目として足す)、
  `boundary_cells` のキーが `valid_key` を通ること、`boundary()` の TTL とズーム下限
- `render::fill_rings_rgba`: 矩形が塗られる / 穴が抜ける / 画面外のポリゴンで何も書かない・panicしない /
  頂点を通る走査線で塗りが裏返らない / 交点が奇数個になる退化ケースで壊れない
- `render::stipple_rgba_into_overlay`: `spacing` ごとに1点だけ置く / 透明画素には置かない /
  寸法が違ってもpanicしない(`ink_radar_into_overlay` の既存テストと同じ形)
- `disaster::fill_alpha`: 5段の境界値(0/4/5/14/15/39/40/99/100/166)
- `disaster::parse_sites`: `CHIDAN_CODE` を `"JP12208"` → `"12208"` として読む /
  `"JP"` で始まらない値・null・空を空文字にする / 既存の座標畳み込みが壊れていないこと
  (既存テストの実応答サンプルに `CHIDAN_CODE` を足して固定する)
- `disaster::fill_alpha`: 5段の境界値(0/4/5/14/15/39/40/99/100/166)
- `choropleth::tally`: `muni_code` をキーに積むこと / 同じコードに複数地点が落ちたときの
  合算と最多種別の決まり方を固定する / コードが空の地点を無視する
- `choropleth::build_layer`: **7桁が違っても丸めた5桁が同じなら同色で塗られること**
  (横浜市の2区域、広島市の8区。§2.4) / 記録の無い市区町村は塗らない / 視野外の区域を塗らない
- `choropleth::area_summary`: 中心がポリゴンの中/外
- `render` / `build_overlay` の複数層: 配列の順序どおりに重なること(コロプレスが雨雲の下)、
  空配列で従来と同じ結果になること

実データを使う確認は `#[ignore]` に置く(`cargo test --release -- --ignored`)。

## 9. 対象外・正直な制約

- **地方では画面に市区町村が1〜2個しか入らない**(§0.1)。都市部は z11 で9〜21区域が入るが、
  地方で「見比べる図」にするには Stage B が要る。Stage A だけの状態で
  「思っていたのと違う」と感じる余地は残る。
- **境界は簡略化した形**(§2)。海岸線や入り組んだ市境は実際の形と数画素ずれる。
  面積比では香川県17市区町村すべてが98.5〜101.0%だが、境界付近の1点がどちらの市区町村かを
  問うと約97%まで落ちる。塗りの用途では問題にならないが、**この境界を「ここは○○市の中か」の
  判定に使わない**(ステータス行の市区町村名は目安として出す)。
  z15以上で縁取りを出さないのも同じ理由。
- **NIEDと境界データの版ずれは検出しない。** 全63,849件のうち那珂川市の1件は、NIEDが
  2018年の市制施行前のコード(`40305`)のままで、どの区域にも当たらない。同種のずれが
  今後の合併で増えても、その市区町村が塗られなくなるだけで警告は出ない。
  実装時に「コードが集計表にあるのに区域が見つからなかった件数」をデバッグ出力で数えて
  規模を把握する。
- **政令市の対応表は2市に固定した実測依存**(§2.4)。JMAが将来ほかの政令市も区単位へ
  変えたら、その市が塗られなくなる。表の網羅性はテストで固定するが、
  データ側の変更は検出できない。
- **件数は「記録の件数」であって被害の大きさではない。** 記録の粗密は当時の報告体制にも
  左右される。濃い色を「危険度」と読ませない書き方を `docs/MANUAL.md` に入れる。
- **面積あたりの密度にしていない。** 広い市町村ほど件数が多く出る偏りが残る。ポリゴンから
  面積は計算できるので密度へ切り替える余地はあるが、記録件数の粗密が報告体制由来である以上、
  面積で割ると別の偏りを足すだけになりかねないので今回はやらない。
- **braille/edge の見え方は机上の計算のみ。** 疎な点描の間隔(8画素)は
  「braille セル8個に1点」という計算から置いた値で、実機で確かめていない。
  §7 の手順5で実際に走らせて詰める。
- **コロプレスと雨雲を同時にONにしたときの見分けは未確認。** 構造(面 vs まだら)と
  濃さの差で分かる想定だが、実機で確かめる。
- **気象庁 bosai エンドポイントには利用条件の明文が無い。** 気象庁ホームページ全体の
  利用ルール(出典明記で再配布・商用可)には従うが、このAPI自体は開発者向けに
  文書化されていない。雨雲ナウキャストのタイルと同じ立場で、予告なく変わりうる
  (`cache-control: max-age=60` / `last-modified: 2026-08-12`)。
  取れなくなったら塗りを出さずマーカー表示へ落ちる(§2.8)。
- **境界データは1回の通信が要る。** レイヤをONにして初めて入る地方で、圏外だと
  塗りが出ない(件数も同じく通信が要るので、可用性は実質変わらない)。
  一度取れば fresh 180日・stale無制限で、再訪でも再起動でも通信しない。
- **`CHIDAN_CODE` の追加で既存のディスクキャッシュが1回無効になる**(§1.1)。
  アップグレード直後に圏外だと、過去に見た土地でも何も出ない。
