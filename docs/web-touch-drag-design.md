iPhone(web版)のドラッグ操作を、①地図パンを指の動きに追従させる ②メニュー/距離ゲージの
ドラッグ方向を直感どおりにする、の2点で作り直すための設計。タスク#87。

対象コード: `web/touch-overlay.js`(タッチ→キー変換) / `src/ui.rs`(Focus別のキー解釈・イベント合流) /
`src/focus.rs`(Focus定義) / 新規 `src/dragmode.rs`。
状態: 設計のみ。実装は未着手。

## 1. 現状の仕組み

web版は ttyd(xterm.js)経由でブラウザから操作する。`web/touch-overlay.js` が

```
touchmove の dx/dy → PX_PER_STEP(24px)ごとに矢印キー1回 → 合成KeyboardEvent
  → xterm.js → ttyd → WebSocket → pty → termmap(crossterm の Event::Key)
```

という離散ステップ変換を行う。ブラウザ→termmap の経路はこのキー変換と、`term.paste()` を使う
専用マーカー(ライブ現在地 `\u{1}GPS\u{1}...`、`src/ui.rs:2332-2350`)の2本がある。
termmap→ブラウザの経路は OSC エスケープ(効果音9999 `src/sound.rs:129-135`、
音声案内9998 `src/voice.rs:126-134`、実画像1337 `src/render.rs:416`)がある。

現状 `DRAG_MAP`(`web/touch-overlay.js:81`)は `true` 固定で、termmap 側の Focus は JS に伝わっていない。

## 2. 問題1: 地図パンが指に追従しない

### 2.1 実際に起きていること

3つの要因が重なっている。

**(a) ゲインが約0.45倍**

termmap 側の1キーあたりの移動量は `fine = oh / 64.0`(`src/ui.rs:2136`)。`oh` は地図領域の出力ピクセル
高さで、braille なら `map_rows*4`、AA なら `map_rows*2`(`src/ui.rs:532`)。どちらでも
「1キー = 地図領域の高さの 1/64」で、画面上の見た目では約 0.61 行分になる。

iPhone(端末領域の高さ約700 CSS px・40行想定)なら 1行 ≈ 17.5px なので、

| | 値 |
|---|---|
| 指を24px動かして送るキー | 1回 |
| そのとき地図が動く量 | 約10.7 CSS px 相当 |
| ゲイン | 約0.45倍 |

指が動いた距離の半分以下しか地図が動かない。X軸も `fine` は `oh` 基準の共通値なので同様(約0.48倍)。

**(b) 送ったキーの大半が捨てられている**

`src/ui.rs:1297-1309` に、パン系キーが溜まっている間は「溜まった分を最新の1個へ間引く」処理がある。

```rust
while let Ok(true) = event::poll(std::time::Duration::from_millis(0)) {
    match event::read()? {
        Event::Key(next) if is_pan_key(next.code) => ev = Some(Event::Key(next)),
        other => { ev = Some(other); break; }
    }
}
```

`ev` を上書きするだけなので、間引かれたキーの移動量は**そのまま消える**。JS が `sendPanDelta` で
1回の touchmove に対し最大 `MAX_STEPS_PER_TICK`(20回)まで送っても、termmap が1フレームで
適用するのは1回分だけになる。指を速く払うほど乖離が大きくなり、「速く動かすほど重い」挙動になる。

**(c) 指の移動量でなく押した回数と間隔で速度が決まる**

termmap には `pan_streak` による加速がある(`src/ui.rs:2127-2144`)。同方向のキーが220ms以内に続くと
streak が伸び、`step = fine * (1 + streak*0.35)`(上限 `fast = oh/4`)まで最大8倍に増える。
これはキーボードで押しっぱなしにしたときのための仕組みで、ドラッグ由来のキーと区別できない。

結果、指1pxあたりの地図移動量は 0.45倍〜3.5倍の範囲で勝手に変動する。指の位置と地図の位置が
対応しないため、「つかんで動かしている」感覚にならない。

### 2.2 `PX_PER_STEP` を小さくするだけでは直らない

(a)だけを見れば `PX_PER_STEP` を 24 → 11 程度に下げればゲインは1:1に近づく。しかし

- (b)により、送るキーが増えるほど間引かれて捨てられる割合が増える。1フレームに適用されるのは
  常に1キー分なので、**滑らかさの上限は「1フレームあたり `fine`×加速」に張り付く**。
  ステップを細かくするほど捨てる量が増え、速いスワイプでの追従はむしろ悪化する。
- `MAX_STEPS_PER_TICK`(20)は(b)の間引きより手前にある上限で、実際には到達する前に無意味化されている。
  この定数を触っても体感は変わらない。
- (c)は JS 側からは制御できない。

つまり定数調整では解決せず、変換方式そのものを変える必要がある。

### 2.3 目標とする式

```
地図の移動量[出力px] = 指が横切ったセル数 × 1セルあたりの地図の出力px
                     = 指の移動量[CSS px] / 端末の寸法[CSS px] × 端末の桁数(行数)
                       × (地図領域の出力寸法 / 地図領域の桁数(行数))
```

**指の下にあるものが指についてくる**、が目標。指が横切ったセル数と、地図が動くセル数を
一致させる。加速も量子化も挟まない。

左袖が出ている画面では地図領域が端末より狭いので、「指が画面の1/4を横切ったら地図も
*地図領域の* 1/4動く」ではない点に注意(それだと指より地図が遅れる)。動かすのは
あくまで指が横切ったセル数ぶんで、§6.2 の式がそうなっている。

## 3. 問題2: ドラッグ方向がFocusで変わらない

### 3.1 方向の正解は「地図と同じキー極性」ではない

`DRAG_MAP=true` は「コンテンツを指につかませる」極性で、指を右へ払うと `ArrowLeft` を送る
(`web/touch-overlay.js:389-390`)。地図はこれで正しい。`ArrowLeft` は `cx -= step` で中心が西へ動き、
地図の絵は指と同じ右方向へ流れる。

一方、一覧のカーソルや距離ゲージは「表示内容がスクロールする」のではなく「選択位置そのものが動く」。
指を下へ動かしたのに `ArrowUp` が送られてカーソルが上へ行くため、指と反対に動いて見える。
距離ゲージも同じで、指を右へ動かすと `ArrowLeft` が送られて距離が減る。

体感を揃えるには、**キーの極性は地図と逆にする必要がある**。タスク名の「地図と揃える」は
見た目の追従感を揃えるという意味で、送るキーを地図と同じにするという意味ではない。実装時に
取り違えやすいので明記しておく。

| 種類 | 指を右/下へ動かしたとき | 送るべきキー | 極性 |
|---|---|---|---|
| 地図(ビューポート) | 地図の絵が右/下へ流れてほしい | ArrowLeft / ArrowUp | 反転 |
| 一覧カーソル・ゲージ | カーソル/つまみが右/下へ動いてほしい | ArrowRight / ArrowDown | そのまま |

## 4. 設計方針

問題1と問題2は独立した2本の通路で解く。

| 通路 | 向き | 手段 | 解決する問題 |
|---|---|---|---|
| A | ブラウザ → termmap | `term.paste()` の専用マーカー `\u{1}PAN\u{1}` | 問題1(追従) |
| B | termmap → ブラウザ | OSC 9997 | 問題2(方向)＋通路Aのケイパビリティ検出 |

軸モードの判定は Rust 側の1関数に集約し、通路Bの通知内容と、通路Aで受けたパン量を適用してよいかの
判定の両方に同じ関数を使う。JS 側に Focus の対応表を持たせない(Focus が増えたときの二重管理を避ける)。

## 5. 通路B: 軸モードの通知(OSC 9997)

### 5.1 番号と形式

```
ESC ] 9997 ; <version> ; <xy> BEL
例: \x1b]9997;1;pp\x07   (地図)
    \x1b]9997;1;nc\x07   (一覧: 横は無効・縦はカーソル)
    \x1b]9997;1;cn\x07   (距離ゲージ)
```

9998(音声)・9999(効果音)の隣で、既定用途(0-9=タイトル、10-19=色、52=クリップボード、1337=iTerm2画像)と
衝突しない私的な番号。データ部に `;` を含める形式は OSC 8(ハイパーリンク)と同じで、xterm.js の
OSCパーサは識別子を最初の `;` までで切り、残り全体をハンドラへ渡す。version を先頭に置き、
将来フィールドを足せるようにする。

認識しない端末(通常のターミナル)では無視される。既存の9998/9999と同じ扱い。

### 5.2 Rust側

新規 `src/dragmode.rs`(`src/focus.rs` の隣、`src/main.rs` に `mod dragmode;` を追加):

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub(crate) enum Axis { Pan, Cursor, None }

/// Focus から (X軸, Y軸) の意味を決める。§3.2 の表がそのままこの関数になる。
pub(crate) fn axes(focus: &Focus) -> (Axis, Axis)

/// ブラウザ(web/touch-overlay.js)へ現在の軸モードを通知する。
/// sound.rs::emit_web_sound_signal と同じ書き方(print! + flush)。
pub(crate) fn emit_web_drag_mode(axes: (Axis, Axis))
```

送出は `src/ui.rs` のフレーム末、`out.flush()?`(現 `src/ui.rs:939`)の直前1か所。

```rust
let ax = dragmode::axes(&focus);
if prev_axes != Some(ax) || drag_mode_req_pending {
    dragmode::emit_web_drag_mode(ax);
    prev_axes = Some(ax);
    drag_mode_req_pending = false;
}
```

Focus は `interactive()` の中の30か所以上で書き換わる(非同期ジョブの完了で勝手に変わる箇所もある。
例: 周辺検索の結果適用で `Focus::Map` → `Focus::PoiList` `src/ui.rs:1195`)。変更箇所ごとに通知を
足すのではなく、フレーム末で前回値と比較する方式にして呼び出しを1か所に閉じる。

`Focus` は `String` を持つため `PartialEq` を導出していないが、比較するのは `(Axis, Axis)` なので
`focus.rs` には手を入れない。

### 5.3 ブラウザ再読み込みへの対応

ページを再読み込みすると JS 側の状態は消えるが、termmap 側の Focus は変わらないので通知が飛ばない。
JS 初期化時と `visibilitychange` での復帰時に、通路Aと同じ paste マーカーで再送を要求する。

```
\u{1}DRAGMODE?\u{1}
```

Rust 側はこれを受けたら `drag_mode_req_pending = true` を立てるだけ(次フレームで送出)。
JS 側の初期値は `p,p`(地図)とし、要求の応答が来る前でも地図では正しく動くようにする。

### 5.4 ケイパビリティ検出を兼ねる

JS は OSC 9997 を1回も受け取っていない間、通路A(§6)を使わず現行のキー変換方式のまま動く。
これにより「新しい overlay + 古い termmap」の組み合わせでも、パン量の paste が検索欄へ
文字として入るような事故が起きない。overlay は `scripts/build-web-index.sh` が同一リポから
埋め込むためバージョン不一致は通常起きないが、ブラウザが `index.html` をキャッシュしている
場合に発生しうる。

## 6. 通路A: パン量の転送(paste マーカー)

### 6.1 形式

ライブ現在地(`src/ui.rs:2336`)と同じ SOH 区切りの専用マーカーにする。`term.paste()` は
bracketed paste で送られるので、制御文字を含めても1つのテキストとして届く。

```
\u{1}PAN\u{1}<fx>\u{1}<fy>\u{1}
例: \u{1}PAN\u{1}0.0132\u{1}-0.0041\u{1}
```

`fx` / `fy` は**指の移動量を端末ビューポートの幅/高さで割った比**(小数4桁)。CSS px でも
セル数でもなく比にするのは、xterm.js の内部APIからセル寸法を取りに行かずに済み、
DPR・フォントサイズ・画面回転に影響されないため。符号は指の移動方向そのもの(右/下が正)で、
反転は Rust 側で行う。

1回あたり約25バイト(+ bracketed paste の前後12バイト)。30Hz で 1.1KB/s 程度。
現行のキー方式は速いスワイプで1tickに20キー=60個の合成KeyboardEvent を dispatch するので、
ブラウザ側の処理コストはむしろ下がる。

### 6.2 Rust側の受け口

```rust
Some(Event::Paste(s)) if s.starts_with("\u{1}PAN\u{1}") => { /* §6.3 で合算済みの値を適用 */ }
```

比 → 出力ピクセルの換算は、端末の桁数/行数(`cols` / `tr`)と地図領域(`map_cols` / `map_rows` / `ow` / `oh`)の
両方を Rust が持っているので Rust 側で完結する。

```rust
let dx_out = fx * cols as f64 * (ow as f64 / map_cols as f64);
let dy_out = fy * tr   as f64 * (oh as f64 / map_rows as f64);
cx -= dx_out;   // 指と同じ向きに地図が流れる(§3.1)
cy -= dy_out;
```

左袖やステータス行のぶんも含めて正確に換算されるので、ゲインの調整定数は要らない。

適用条件:

- `dragmode::axes(&focus)` の該当軸が `Axis::Pan` のときだけ適用する。X軸とY軸を独立に判定する
  (`PoiList` は X だけ適用される)。`Pan` でない軸の値は捨てる。
- `fx` / `fy` は有限かつ `-1.0..=1.0` にクランプする。パース失敗・NaN・範囲外は無視
  (GPS マーカーが `is_finite()` と範囲チェックをしているのと同じ扱い)。
- 適用したら `pan_streak = 0` / `last_pan_dir = None` にリセットする。キーボードの加速と混ざらないようにする。

### 6.3 溜まった分は捨てずに合算する

既存のキー間引き(`src/ui.rs:1297-1309`)は最新1個で上書きするが、パン量は相対値なので
**足し合わせれば取りこぼしがゼロになる**。これが §2.1(b) の直接の解決になる。

```rust
// 既存のパンキー間引きブロックの隣に置く
let mut pan_dx = 0.0f64;
let mut pan_dy = 0.0f64;
if matches!(&ev, Some(Event::Paste(s)) if is_pan_paste(s)) {
    // ev の分を pan_dx/pan_dy へ足してから、溜まっている分を drain して足し込む。
    // PAN 以外のイベントが来たら ev をそれに差し替えて break する(合算値は保持したまま)。
}
// match ev の前に、pan_dx/pan_dy が非ゼロなら適用する
```

`ev` を上書きしても合算値は別変数に残るので、途中で別のキーが割り込んでも移動分は失われない。
描画が遅れて数フレーム分溜まっても、指を離した時点の位置には必ず追いつく。

### 6.4 JS側

| 項目 | 現状 | 変更後 |
|---|---|---|
| `DRAG_MAP`(81行) | `true` 固定 | 削除。`dragAxes = {x:'p', y:'p'}` を OSC 9997 で更新 |
| `xKey/yKey`(389-390行) | `DRAG_MAP` で分岐 | 軸モードで分岐(`p`=反転 / `c`=そのまま / `n`=送らない) |
| `sendPanDelta`(395-412行) | 全軸を矢印キーへ | `p` 軸は通路A、`c` 軸は矢印キー、`n` 軸は何もしない |
| `PX_PER_STEP`(63行) | 24(全用途共通) | `c` 軸専用の `CURSOR_PX_PER_STEP`(初期値48程度)へ改名。通路Aが使えない場合のフォールバック時のみ従来の意味で使う |
| `MAX_STEPS_PER_TICK`(70行) | 20 | 据え置き(ピンチとフォールバック用) |
| 慣性(`startGlide`) | 全軸 | `p` 軸のみ。`c` 軸は指を離したら止める |
| 送信レート | touchmove ごと | `p` 軸は 30Hz 上限に間引き、間引いた分は次回へ繰り越す |

`c` 軸のステップを 24 から 48 程度へ広げるのは、一覧のカーソルが1行動くのに指24pxは細かすぎて
狙った項目で止められないため。実機で詰める。

慣性を `c` 軸で切るのは、フリックで一覧が流れて意図しない項目が選ばれるのを避けるため。
`PoiList` / `RoutePanel` / `WaypointList` はカーソル移動のたびに地図が選択地点へ追従して
再描画が走る(`src/ui.rs:1856` 等)ので、慣性で連続移動させると負荷も大きい。

タップ(Enter送出)とピンチ(`+`/`-`)は現状のまま変更しない。

## 7. マウス操作(PC確認用)への影響

`mousedown`/`mousemove`/`mouseup`(`web/touch-overlay.js:547-568`)は同じ `sendPanDelta` を通るので、
変更はマウス側にもそのまま効く。方向の直感はタッチと同じ基準なので、メニュー上でのマウスドラッグも
一緒に直る。破壊的な変化ではないが、以下は確認する。

- PC の物理キーボードから矢印キーを押す経路は一切変えない。`pan_streak` の加速もそのまま残る
  (通路Aを受けたときだけリセットする)。
- xterm.js のテキスト選択との競合は現状のままで、今回は触らない。
- `sawTouch` によるタッチ/マウスの排他も現状のまま。

## 8. 却下した案

### 8.1 方向の判定方法

| 案 | 内容 | 判定 |
|---|---|---|
| A: OSC通知 | Rust が軸モードを送る | **採用**。Focus変更のたびに数バイト。既存の9998/9999と同じ仕組みで確実 |
| B: 画面テキストから推測 | xterm.js のバッファを読んで左袖の有無等を判定 | 却下。レイアウト変更で壊れる。実画像モードでは地図領域がテキストでない。左袖の有無だけでは軸モードまで決まらない(`PoiList` の X はパン、`RoutePanel` の X は無効) |
| C: JS側でキー履歴から状態を推測 | Space→メニュー、Esc→地図 のように JS が状態機械を持つ | 却下。Focus の遷移を二重実装することになる。さらに非同期ジョブの完了で Focus が勝手に変わる箇所があり(`src/ui.rs:1118` / `1146` / `1195` / `1258`)、キー履歴だけでは追随できない |
| D: マウストラッキング(DECSET 1000/1002/1006) | termmap 側でマウス報告を有効にし、JS が touch を mouse に変換して送る。ドラッグの解釈を全部 Rust 側で行う | 却下。方向問題は原理的に消えるが、座標の粒度がセル単位(縦約17px)で滑らかさが出ない。xterm.js はピクセル単位報告(1016)に対応していない。PC でのテキスト選択・コピペを阻害する。既存の overlay がマウスイベントを xterm へ渡さない設計と衝突する。実装量も大きい。将来 termmap 側でタップ位置を使いたくなった場合の選択肢としては残る |

### 8.2 滑らかさの実現方法

| 案 | 内容 | 判定 |
|---|---|---|
| 1: `PX_PER_STEP` を下げる | 24 → 12 や 8 | 却下。§2.2 のとおり間引きで捨てられる割合が増え、速いスワイプでは悪化する |
| 2: 間引きを「捨てる」から「回数を数えて一括適用」へ | Rust 側の合流でキー数を数え `step*n` を適用。あわせて JS が端末実寸から `PX_PER_STEP` を動的算出 | 却下。取りこぼしは直るが量子化が残り、`pan_streak` の加速との干渉も残るため 1:1 にならない。Rust 側を触る点は案3と同じで、実装コスト差はほとんど無い |
| 3: パン専用チャネル + Rust側で合算 | §6 | **採用**。1:1 が式で保証される。加速と分離できる。端数の繰り越しが JS 側で完結し、慣性も連続量で送れる |
| 4: JS 側で先読み描画 | Rust の応答を待たずブラウザ側で地図を動かす | 却下。描画主体は termmap で、ブラウザは端末エミュレータでしかない |

## 11. テスト方針

Rust 側(`cargo test`):

- `dragmode::axes()` を `Focus` の全 variant で検証する。特に `PoiList` が `(Pan, Cursor)`、
  `WanderForm` が `(Cursor, None)` になること。Focus が増えたときにここが落ちるよう網羅的に書く。
- `emit_web_drag_mode()` の出力文字列(`\x1b]9997;1;pp\x07`)。`src/sound.rs` / `src/render.rs:749` の
  OSC テストに倣う。
- パン量マーカーのパース: 正常値 / 範囲外(±1超) / NaN / 数値でない / フィールド不足 / マーカーだけ。
- 比 → 出力ピクセルの換算式を純関数に切り出して検証する(`cols`/`tr`/`map_cols`/`map_rows`/`ow`/`oh` を引数に取る)。

ブラウザ側(自動テスト無し。実機確認の手順):

1. メニュー(Space)を開き、上下ドラッグでカーソルが指と同じ向きに動く。
2. `W` で距離ゲージを開き、右ドラッグで距離が増え、左ドラッグで減る。
3. 地図で指をゆっくり動かし、地図が指についてくる(離した位置と地図の位置が対応する)。
4. 速いフリックで慣性が効き、指を離した後に自然に止まる。
5. 一覧でフリックしても慣性で流れない。
6. PC の Chrome でマウスドラッグと物理キーボードの矢印が従来どおり動く。
7. OSC 9997 が届かない状態(`window.__termmapTouch` から軸モード更新を止める)で、
   従来のキー方式にフォールバックする。

デバッグ用に `window.__termmapTouch` へ現在の軸モードと、手動で軸モードを注入する関数を公開する
(既存の `sendKey` / `sendPanDelta` と同じ扱い)。

## 12. 未確定・リスク

- xterm.js の `registerOscHandler(9997, ...)` がデータ部の `;` を含めて渡すことは OSC 8 と同じ扱いの
  はずだが、ttyd 1.7.7 同梱版で実機確認する。問題があれば区切りを `,` に変える。
- 送信レート 30Hz は目安。pty が詰まった場合に指を離した後も動き続ける遅延が出ないか実機で見る
  (§6.3 の合算受信でフレームごとに全部消費するため理屈上は溜まらない)。
- ゲイン 1:1 が「速すぎる/遅すぎる」と感じる可能性がある。その場合は換算式に固定の係数を1つ入れる
  (端末サイズ依存を残さないため、係数は Rust 側の定数1つに閉じる)。
- 地図領域を覆うフォーム表示中(`map_covered`、`src/ui.rs:932-936`)のドラッグをどう扱うか。
  §3.2 の表では文字カーソル移動(`c,n`)にしているが、実機で邪魔なら `n,n` に倒す。
- `PoiList`(`p,c`)の斜めドラッグでは、X軸のパンが同じフレームのカーソル移動で打ち消される。
  カーソルが動くと選択地点へ地図がスナップする(`cx`/`cy` を選択POIの座標で上書きする)ためで、
  横に払いながら縦にもずれると横パンが戻って見える。これは矢印キー経路でも同じ
  (←→で微パンした直後に↑↓を押すと同様に戻る)既存の挙動で、今回の変更で入ったものではない。
  実機で邪魔なら「カーソルが動いたフレームは横パンを捨てる」か、`PoiList` を `n,c` に倒す。
  どちらも体感で決める話なので実装側で先に倒さない。
- 起動直後、termmap が `EnableBracketedPaste` を出すまでの窓では `term.paste()` が
  bracketed paste で包まれず、マーカーが生のキー入力として解釈される(`Ctrl-A`=住所取得の
  ブロッキングHTTP、`A`=ルート再生 等が誤発火する)。overlay 側は `term.modes.bracketedPasteMode`
  を見て、立つまで送らないようにしてある。ttyd/xterm.js を差し替えたときはこの前提
  (`modes` ゲッターの存在)を確認する。
