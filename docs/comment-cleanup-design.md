ソースコメントの整理方針。対象は `src/**/*.rs`・`build.rs`・`web/*.js` のコメント(`//`・`///`・`//!`、JS は `/* */` も)。
コードそのもの(文字列リテラル・テストデータを含む)は変えない。

## 1. 規則

- タスクID(`#69`・`(#87)`・`タスク#87` の形)を消す。前後の括弧や「タスク」も一緒に消し、文として自然に直す。
  `(#渋滞情報)` のように `#` の後に日本語が続くタスク名も同じ扱いで消す。
  Rust の属性 `#[...]`・色コード(`#808080`)・URL の `#`・画面に出す番号(`#1..#n`)・外部のバグ番号(`Bug#679437`)は対象外。
- 日付(`2026-04-01`・`2026/4/1` 等)を消す。「いつ」の情報が意味を持つ場合は「以前は」「現行の仕様では」等の
  言い方へ置き換える。データの年次(`令和2年国勢調査`)・データ形式の例(`"20260814060000"`)・
  テストが扱う日付そのものは対象外。
- 5行以上続くコメントは、残す価値のある内容(なぜそうしているか・壊れやすい前提・取り違えやすい点)に絞って
  短くする。目安は元の半分以下・原則4行以内。経緯の物語・実測の過程・言い換えの重複は削る。
  設計書への参照(`docs/xxx.md §2.3`)は残す(詳細はそちらにある)。
- 振る舞いの説明を変えない。コメントが指す関数名・定数名・設定キーは一字も変えない。

## 2. 検証

- `scripts/check-comment-only-diff.py`: 変更前後のファイルからコメントを取り除き、残ったトークン列が
  完全一致することを確かめる(コメント以外を変えていないことの機械チェック)。
- `cargo test` と `cargo build --release`。
- `scripts/comment-stats.py`: タスクID・タスク名・日付・5行以上の塊を数える。整理後は、残った塊が
  理由のあるもの(壊れやすい前提の列挙・使い方)だけであることを目視で確かめる。
