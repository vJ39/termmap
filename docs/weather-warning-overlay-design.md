気象警報・注意報(#79)を地図に表示する機能の設計。前提調査:
`docs/weather-warning-data-investigation.md`(#79)。

## 1. 未確定の分岐点(ユーザー判断待ち)

実装方式を2つに絞ったが、どちらを採るかはユーザー判断が必要なため、この設計書はここまでを
決定事項、以降を「両案の設計メモ」として扱う。

| # | 案 | 概要 | 長所 | 短所 |
|---|---|---|---|---|
| A | 視野ベース(PlotLayer方式) | traffic/camera/regulation/disaster(#71-75)と同じ`PlotLayer<T>`(#84)に5レイヤ目として追加。表示範囲(bbox)に懸かるエリアの警報を出す | 実装量が小さい。既存のディスクキャッシュ・TTL・ポーリング・テスト基盤(856行・26テスト)をそのまま流用できる | 「ルート沿いに表示する」という元の要望と厳密には一致しない(今見ている場所の警報であって、これから走る先の警報ではない) |
| B | ルートベース | 確定ルートのポリラインが通過する警報エリアを判定し、ルート区間の色分け/警報一覧をルートパネルや音声案内に出す | 元の要望(ツーリング前に「この先大丈夫か」を知りたい)に忠実 | 新規の設計面が多い(ルート確定時のトリガー、区間の色分け描画、UI置き場)。PlotLayerを流用できない |

判断の材料:
- Aは既存の設定画面ON/OFF・ステータス行件数表示の並びにそのまま乗る(道路交通量/カメラ/通行規制/過去災害と同列)
- Bは「ルート未確定なら出ない」「ルート確定/再計算のたびに判定し直す」という、既存のvoice_guide(#78)や標高プロファイルに近い挙動になる
- 両方やる(Aで常時、Bでルート確定時に強調)という組み合わせも技術的には可能だが、実装量は単純に加算される

以降はどちらの案でも共通して必要な下地(データ取得・境界判定)を先に固め、その後にA/B個別の設計メモを置く。

## 2. データソース(確定・実アクセス確認済み)

| データ | エンドポイント | 内容 | 更新頻度 |

発表される場合が多く、class20sまで細かくしても得られる精度は限定的なため。

## 3. 境界判定(A/B共通の下地)

### 3.1 point-in-polygon

新規の小さい純関数モジュールが要る。既存の`geo.rs`(haversine距離のみ)にも`roadtrace.rs`にも
多角形内外判定は無い。

```
// 新規: src/geoarea.rs (仮称。std のみ・crate:: 参照禁止・単体コンパイル可能、他モジュールと同じ方針)
pub fn point_in_polygon(point: (f64, f64), ring: &[(f64, f64)]) -> bool  // レイキャスティング法
pub fn point_in_multi_polygon(point: (f64, f64), rings: &[Vec<(f64, f64)>]) -> bool // GeoJSON MultiPolygonの穴(内側リング)は今回無視してよいか要確認
```

GeoJSON MultiPolygonは`[polygon, polygon, ...]`で各polygonは`[外周, 穴1, 穴2, ...]`の構造を持ちうる。
気象庁の警報区域に「穴」(ドーナツ状の除外領域)が実在するかは今回のサンプルでは確認できていない
(153件全部は見ていない)。穴を無視して外周のみで判定する簡易実装から始め、誤判定が実測で
出た場合に穴対応を追加する、という段階実装にする。

### 3.2 class10s境界データの持ち方

289KBの静的データで、区域定義自体はほぼ不変(市町村合併等でごく稀に変わる程度)。
既存レイヤ(traffic/camera/regulation/disaster)のような「毎回ネットワークから取ってTTLで
expireする」方式ではなく、**ビルド時に埋め込む**(`include_str!`)方式を採る。

理由: 境界ポリゴンはユーザーの操作(ON/OFF)と無関係に必要になる基礎データであり、ネットワーク
障害時にこれが取れないと機能全体が動かなくなるのは過剰。289KBはバイナリサイズへの影響も
小さい。区域定義が変わった場合はtermmap自体のアップデートで追従する(既存の他データより
更新頻度が低いため許容できる)。

```
// src/geoarea.rs
const CLASS10S_GEOJSON: &str = include_str!("../assets/jma-class10s.json"); // ビルド時同梱
pub fn class10s_regions() -> &'static [Region]; // OnceLockでパース結果をキャッシュ
```

assets/配下に静的データを置く前例は無いため、`assets/`ディレクトリを新設する(camera.rs等の
画像は逐次取得でディスクに保存しない方針なので、これが最初の同梱静的データになる)。

### 3.3 都道府県コードの決定

`area.json`の`class10s[code].parent`が所属都道府県コード(例: `130010`の親は`130000`)。
`offices.json`相当(`area.json`の`offices`キー)は不変データなのでこれも同梱する
(`include_str!`)か、`class10s`のcodeから先頭2桁+"0000"を機械的に導出できるか確認が必要
(実測ではcode体系が概ね規則的だが、確証はまだ取っていない。安全を取るならarea.jsonの
`offices`もclass10sと同様に同梱する)。

## 4. 案A: 視野ベース(PlotLayer方式)の設計メモ

- `PlotItem`実装の`WarningArea { code: String, name: String, ring: Vec<(f64,f64)> /* 表示用に簡略化した外周 */, active_codes: Vec<String> }`を追加
- 表示bboxと交差するclass10s regionを`point_in_polygon`ではなく矩形交差判定(bbox同士)で粗く絞り
  込んでから、該当regionの所属都道府県の`warning.json`を取得(1都道府県=1リクエスト。表示範囲が
  複数県にまたがれば複数リクエスト)
- 描画は`draw_polyline`(regulation.rsと同じ関数)で外周を色分け線描画、または`draw_ring`で
  代表点に警報種別の色マーカーを置く簡易表示から始める(ポリゴン塗りつぶしはrender.rsに
  実装が無く新規実装が要るため、まず線/マーカーで様子を見る)
- fresh TTL: 既存のtraffic(5分)より緩めでよい(警報は随時更新だが5分単位の精度は不要)。
  10〜15分程度を仮案とし、実装時にユーザーと確認
- 設定画面: 末尾(idx=28)に追加。「気象警報」ON/OFF

## 5. 案B: ルートベースの設計メモ

- ルート確定時(`trigger_route`成功時、既存のvoice_guide作り直しと同じフック)に、ルートの
  ポリライン上を`sample_every`(roadtrace.rs既存)で一定間隔サンプリングし、各サンプル点が
  どのclass10s regionに入るかを`point_in_polygon`で判定する
- 連続するサンプル点が同じregionなら1区間にまとめ、regionごとに対応都道府県の`warning.json`を
  取得(ルート全体で高々数県分。視野ベースより通信量は少ない見込み)
- 警報が有るregionだけ、ルート線の色を変える(既存のroute描画色の上に警報色を重ねる、または
  警報区間の脇に印を置く)
- ルートパネル(RoutePanel)またはステータス行に「警報: 濃霧注意報(伊豆諸島北部)」のように
  テキストでも出す(バイクはヘルメット越しに地図の色を見づらいため、テキスト情報の方が実用的
  という考え方もある。案Aでもこの点は同じ)
- 設定画面: 末尾に追加。「ルート沿い気象警報」ON/OFF。ルート未確定時は「ルート未確定」表示

## 6. テスト方針(A/B共通部分)

- `point_in_polygon`/`point_in_multi_polygon`: 単純な矩形・凹多角形・境界線上の点・穴あり(実装する場合)の単体テスト
- `class10s_regions()`: 同梱JSONのパースが壊れていないこと(件数・特定コードの存在確認)
- 警報コード→色/表示名のマッピング: 既存のRegulationKindと同じ構造(enum+color()+label())で
  テスト可能
- warning.json解析: 実際のレスポンス例(投資調査doc記載のサンプル)を使った純関数テスト
  (parse_traffic/parse_closuresと同じパターン)
- ネットワークに触れる部分は`#[ignore]`の実アクセステストで担保(このセッションの既存パターン)
