地図に重ねる4種類のプロットデータ(道路交通量・主要道路・道路ライブカメラ・通行規制)を
ディスクへ永続化し、種類ごとに違うTTLで期限切れにする仕組みの設計。目的は2つで、
**外部APIの呼び出し削減**と、**オフライン/取得失敗時に直近データを出し続けること**。

対象コード: `src/traffic.rs` / `src/roadsearch.rs` / `src/camera.rs` / `src/regulation.rs` /
`src/ui.rs` の `traffic_*`・`major_roads_*`・`camera_*`・`regulation_*` ブロック。
参考にした既存実装: `src/searchcache.rs`(バージョンヘッダ+TTL+LRU) / `src/tiles.rs`(mtime TTL) /
`src/route.rs`(キー1件=1ファイル) / `src/fsutil.rs`(アトミック保存)。

状態: 実装済み(`src/mesh.rs` / `src/plotcache.rs` / `src/plotlayer.rs`)。
設計から変えた点は §15 に追記した。

## 1. 現状(実測)

### 1.1 4レイヤに同じコードが4回並んでいる

`src/ui.rs` の 951〜1070行に、ほぼ同一の取得ブロックが4つある(合計約120行)。共通の作りは次のとおり。

| 項目 | 値 | 実体 |
|---|---|---|
| 取得範囲 | 視野中心の ±900px (`MARGIN_PX`) | `pixel_to_deg(cx∓900, cy∓900, z)` で緯度経度bboxへ変換。**bboxの実寸はズームに依存する** |
| 再取得の条件A | 視野中心が前回bboxの外に出た | 中心1点だけを見る(視野の四隅は見ていない) |
| 再取得の条件B | 前回取得から90秒経過 (`REFRESH`) | 4レイヤとも同じ値 |
| 取得方法 | `std::thread::spawn` + `mpsc` で1レイヤ1ジョブ | 同時に走るのはレイヤごとに最大1本 |
| 結果の適用 | 受信した `Vec` で丸ごと置き換え | — |

`MARGIN_PX` が900pxもあるのは、条件Aが中心1点しか見ていないため、余白を大きく取らないと
視野の縁にデータが無い状態になるから。つまり余白は中心判定の弱さを埋めるための代償になっている。

### 1.2 現状の問題

**(a) 定置していても90秒ごとに叩き続ける。** 3レイヤをONにして1時間画面を開いたままにした場合の
リクエスト数は次のとおり(bboxが2メッシュにまたがる想定)。

| レイヤ | 1時間あたり | 内訳 |
|---|---|---|
| 道路交通量 | 40 | JARTIC WFS × 40 |
| 主要道路 | 40 | Overpass × 40(1回が重いクエリ) |
| 道路ライブカメラ | 40 | 整備局ページ(全カメラ入り)× 40 |
| 通行規制 | 120 | (HTML 1 + メッシュJSON 2) × 40 |
| 合計 | **約240** | |

**(b) 更新間隔がデータの更新周期と合っていない。** 道路交通量は5分値で、しかも観測から取得可能に
なるまで約25分のラグがある(`traffic.rs` の `OBSERVE_LAG_MIN=25` / `WINDOW_MIN=10`)。90秒ごとに
叩いても新しい値は存在しない。主要道路(OSMの trunk/primary 幾何)は月単位でしか変わらないのに、
最も重いOverpassクエリを90秒ごとに投げている。

**(c) 取得失敗でオーバーレイが消える。** `camera::fetch_cameras` と `regulation::fetch_closures` は
失敗時に `Vec::new()` を返す(`camera.rs:82-102` / `regulation.rs:117-152`)。呼び出し側は
「0件」と「失敗」を区別できないため、圏外に入った瞬間に `camera_points` / `regulation_events` が
空で上書きされ、直前まで見えていた通行止めがトンネル1本で消える。道路交通量と主要道路は
`Result` を返すので `Err` 時は前回値を保持する(`ui.rs:977`, `ui.rs:1008`)——4レイヤで挙動が割れている。

**(d) 再起動で全部消える。** 圏外でアプリを開き直すと、直前まで持っていた規制情報が何も出ない。

**(e) 広域ズームで無防備。** ズーム下限が無いので、z8で開くと1800px = 数百km四方のbboxで
JARTIC/Overpassを叩く。`traffic.rs` 冒頭は「範囲を絞らずに叩くとバックエンドがOOMで落ちる」と
実測を残しており、広域クエリは相手側の負荷として無視できない。

### 1.3 既存のディスクキャッシュ実装(この設計が倣うもの)

| 実装 | 形式 | 期限 | 上限 | 備考 |
|---|---|---|---|---|
| `searchcache.rs` | 1ファイルにTSV全件・先頭にバージョン行 | 90日(`created_at`基準) | 3000行・LRU破棄 | 保存は全件書き直し |
| `tiles.rs` | 1タイル=1ファイル | 30日(mtime基準) | **無し** | 実測 428MB / 21,076ファイル |
| `route.rs` | 1キー=1ファイル(FNV-1aハッシュ名) | **無し** | **無し** | 実測 14MB / 126ファイル |

`tiles.rs` は雨雲タイルだけディスク保存を拒否している(`tiles.rs:41-46`)。理由は
「キーに basetime が入るのでヒット率がほぼゼロ」「30日TTLで古い降水が現在として描かれる危険」。
今回の4種はいずれもキーに時刻を含めない(§5)ので前者に該当せず、後者は年齢表示(§10)で潰す。

## 2. 設計方針

1. **キャッシュ単位を、取得元が持つ自然な単位に合わせる。** bboxの生の緯度経度をキーにすると
   1pxパンするたびに別キーになりヒットしない。通行規制は1次メッシュ、カメラは地方整備局と、
   取得元が既に単位を持っている。持っていないもの(交通量・主要道路)にはJISメッシュを当てる(§5)。
2. **TTLを2段にする。** 「再取得を抑止する期間(fresh)」と「オフラインで表示だけは許す期間(stale)」を
   別の値にする。これで API削減 と オフライン表示 の両方を1つの設計で満たす(§4)。
   staleを出すときは必ず経過時間を画面に出す(§10)。
3. **ディスクI/Oを全部ワーカースレッド側に置く。** 「ディスクを見て、無ければネットを叩き、
   保存して返す」を1本のジョブにする(`tiles.rs::fetch_tile` と同じ形)。UIスレッドは
   `mpsc` から受け取るだけで、既存の受信コードは形を変えずに済む。

## 3. TTL(有効期限)

| 種別 | fresh(再取得抑止) | stale上限(オフライン表示) | 根拠 |
|---|---|---|---|
| 道路交通量 | **5分** | **60分** | 元データが5分値。さらに観測から約25分のラグがあるため、5分より短い間隔で叩いても新しい値は存在しない。雨雲の `RADAR_REFRESH_SECS = 300`(「ナウキャスト自体が5分更新なので、これより短くしても新しい情報は無い」)と同じ理屈・同じ値。60分を超えると時間帯による交通量プロファイルが変わるため、現況としては示さず破棄する |
| 主要道路 | **30日** | 無期限(GCで破棄されるまで) | OSMの trunk/primary 幾何は月単位でしか変わらない。地図タイルと同じ性格のデータなので `tiles.rs` の `TILE_TTL`(30日)と同じ値を使う。古い道路線形が誤誘導になることはない(新設道路が出ないだけ)ので、staleに上限を設けない |
| 道路ライブカメラ | **7日** | 無期限(GCで破棄されるまで) | キャッシュ対象は設置位置のみ(§6.3)。カメラの新設・撤去は週〜月単位なので、7日あれば「新しいカメラが見えない」窓を実用上問題ない範囲に抑えつつ、1回の旅行中の再取得をほぼゼロにできる。位置が数日古くても実害が無いのでstale上限は設けない |
| 通行規制 | **10分** | **24時間** | 数十分〜数日で変わり、かつ通行止めは安全に直結するのでfreshは短くする。一方、災害・工事による通行止めは日単位で続くため、オフラインでは「N時間前時点の規制」として出す価値がある。24時間を超えたものは破棄する |

fresh TTL は「その期間内なら通信しない」の意味で、`REFRESH = 90秒` に代わって**再取得要否の唯一の判断基準**になる。

## 4. キャッシュ単位とキー設計

### 4.1 単位の選定

| 種別 | 単位 | キー | 選定理由 |
|---|---|---|---|
| 道路交通量 | 1次メッシュ(JIS X 0410、約80km四方) | メッシュコード4桁(例 `5339`) | 取得元にbbox以外の単位が無い。観測点は直轄国道の常時観測点のみで疎なので、80km四方でも1回のレスポンスは小さい。規制と単位を揃えると被覆計算を共有でき、両方ONのときに境界も揃う |
| 通行規制 | 1次メッシュ | 同上 | **取得元がメッシュ単位でファイルを分けている**(`TukoKisei/{mesh}.json`)。`regulation.rs` は既に `primary_mesh_codes()` でbboxをメッシュへ分解している |
| 道路ライブカメラ | 地方整備局CD(81〜90) | 2桁(例 `83`) | **取得元が整備局単位でページを持つ**。`fetch_cameras` は整備局ページを丸ごと取ってからbboxで絞っている(`camera.rs:98-102`)ので、絞る前の全件を持てば全国でも最大10エントリで済み、同一整備局内のパンは必ずヒットする |
| 主要道路 | 2次メッシュ(1次を8×8分割、約10km四方) | メッシュコード6桁(例 `533945`) | 1次メッシュでは幾何が重すぎる(都心の80km四方の trunk/primary は数MB級かつ Overpass の `[timeout:25]` に収まらない恐れ)。同じJISメッシュ体系の下位レベルを使えば語彙が1つで済む |

1次メッシュは緯度40分×経度1度で、緯度35度では約74km(南北)×91km(東西)。
2次メッシュは緯度5分×経度7分30秒で、同じく約9.3km×11.4km。

### 4.2 ズーム下限と1画面あたりのセル数

bboxは中心±900px、つまり1辺1800pxぶん。緯度35度での地上解像度は
`156543.03 × cos(35°) / 2^z ≒ 128,240 / 2^z` m/px なので、必要セル数は次のようになる。

| ズーム | 1800pxの実寸 | 1次メッシュ(必要枚数) | 2次メッシュ(必要枚数) |
|---|---|---|---|
| z10 | 約225km | 12〜16 | — |
| z11 | 約113km | 4〜9 | — |
| z12 | 約56km | 1〜4 | 25〜36 |
| z13 | 約28km | 1〜4 | 9〜16 |
| z14 | 約14km | 1 | 4〜6 |
| z15 | 約7km | 1 | 1〜4 |
| z16 | 約3.5km | 1 | 1〜4 |

セルに分割すると「1回のbbox取得」が「N回のセル取得」に化けるため、広域では**今より通信が増える**。
これを防ぐために、レイヤごとにズーム下限を置く。下限より広域では取得しない(既にあるキャッシュは
描いてよい)。ステータスには `🚗広域では非表示` のように出す。

| レイヤ | ズーム下限 | 下限での必要セル数 |
|---|---|---|
| 道路交通量 | z11 | 最大9(1次) |
| 通行規制 | z11 | 最大9(1次) |
| 主要道路 | z14 | 最大6(2次) |
| 道路ライブカメラ | 下限なし | 整備局は最大でも1〜2 |

加えて安全弁として、1回の判定で必要なセルが `MAX_CELLS_PER_JOB = 9` を超えたら取得しない。
これは(e)の広域クエリ問題への対処も兼ねる。

主要道路の下限がz14と厳しいのは、このレイヤが**まだ描画されていない**(`docs/road-traffic-spec.md` §1、
線色付けは未実装)ため、当面は取得コストを最小に寄せてよいという判断による。描画を実装した時点で
z13へ下げるかを再検討する。

### 4.3 セル被覆に変わることで消えるもの

- `MARGIN_PX = 900` は不要になる。判定が「中心が前回bboxの内か」から
  「今の視野を覆うセルが全部手元にあるか」に変わるので、余白で誤魔化す必要がなくなる。
  セル自体が視野より十分大きい(z14で1次メッシュ1枚 vs 視野14km)ため、余白は構造的に確保される。
- `traffic_bbox` / `camera_bbox` 等の「前回取得bbox」変数も不要になる(セル表がその役割を持つ)。

### 4.4 セルbbox→既存fetch関数への受け渡し

セルを緯度経度bboxへ戻して既存の `fetch_*` に渡す。**取得関数側のシグネチャは変えない**
(カメラと通行規制を除く。§7.2)。

1点だけ注意がある。1次メッシュの矩形をそのまま `regulation::fetch_closures` に渡すと、内部の
`primary_mesh_codes()` が `floor` で境界を拾って隣のメッシュまで含めることがある
(`lat_max` がちょうど境界上のとき)。セル矩形は各辺を `1e-6` 度だけ内側へ寄せて渡す。

## 5. ファイル配置とフォーマット

### 5.1 配置

```
~/.config/termmap/plot-cache/v1/
    traffic/5339.json          # 1次メッシュコード
    regulation/5339.json       # 1次メッシュコード
    roads/533945.json          # 2次メッシュコード
    camera/83.json             # 地方整備局CD
```

- **1キー=1ファイル**にする(`tiles.rs` / `route.rs` と同じ)。理由は3つ。
  (a) 保存が該当セル1件だけの書き込みで済む。主要道路は1セルで数百KBになるため、
  `searchcache.rs` のような全件書き直しはコストが見合わない。
  (b) 壊れたときの被害がそのセルに限定される。
  (c) **termmapを2窓で開いても互いのエントリを消さない**。全件を読んで書き戻す方式
  (`searchcache.rs` の現状)は、片方の保存がもう片方の追加を巻き戻す。
- ファイル名にハッシュは使わない。キーが既に短い整数(メッシュコード/整備局CD)なので、
  そのまま名前にすれば人が見て中身を判断できる(`route.rs` のハッシュ名より扱いやすい)。
- **バージョンをディレクトリ名に持たせる**(`v1`)。形式やTTLの意味を変えたら `v2` へ上げるだけで
  旧データが丸ごと参照されなくなり、GC(§8)が旧ディレクトリを削除する。
  `searchcache.rs` の先頭バージョン行と同じ考え方を、ディレクトリ単位に置き換えたもの。

### 5.2 ファイルの形

`serde_json` で1ファイル1オブジェクト。プロジェクトは既に `serde` / `serde_json` に依存している。

```json
{"v":1,"key":"5339","fetched_at":1755330000,"data_at":1755328500,"items":[ ... ]}
```

| フィールド | 意味 |
|---|---|
| `v` | 形式バージョン(ディレクトリ名と二重化。移行途中の混在を弾く) |
| `key` | 自分のキー。ファイル名との不一致を検出したら破棄する(取り違え・コピー事故の保険) |
| `fetched_at` | 取得完了時刻(epoch秒)。fresh/stale判定はこの値で行う |
| `data_at` | データ自身の時刻(epoch秒)。**交通量のみ意味を持つ**(§5.4)。他はfetched_atと同値 |
| `items` | 取得結果本体 |

期限判定にmtimeを使わない点が `tiles.rs` と違う。`tiles.rs` は期限切れを「無かった」扱いにするので
中身を読まずmtimeだけで判定できるが、この設計はstaleでも中身を表示するため結局ファイルを読む。
mtimeはGC(§8)がファイルを開かずに古い順で並べるためだけに使う。

保存は `fsutil::write_atomic(path, bytes, None)` を使う(一時ファイル→`rename`)。
`searchcache.rs` が同等の関数を自前で持っているのは、単体で `rustc` に通すための制約によるもので、
今回はその制約を負わないので既存の共通実装を使う。

### 5.3 items の形(種別ごと)

原則は **「取得関数が返す型をそのまま保存する」**。こうするとワーカーが
「ディスクから読む」と「ネットから取る」を透過的に差し替えられる。

| 種別 | items | 備考 |
|---|---|---|
| 道路交通量 | `[{"lat":..,"lon":..,"volume":..}]` | `TrafficPoint` に `Serialize/Deserialize` を derive |
| 主要道路 | `[{"pts":[[lat,lon],..],"oneway":false}]` | `fetch_major_roads` の戻り値 `Vec<(Vec<(f64,f64)>,bool)>` に対応。座標は**位置配列**で持ち(オブジェクトより約6割小さい)、**小数6桁に丸める**(約0.1m。z16の1px≒2.4mなので描画には影響しない) |
| 通行規制 | `[{"line":[[lat,lon],..],"kind":"Closed"}]` | `RegulationKind` を文字列で持つため `to_name`/`from_name` を追加する(元の `kisei_naiyo_cd` は `ClosureEvent` に残っていない) |
| 道路ライブカメラ | `[{"id":..,"lat":..,"lon":..,"name":..}]` | **唯一の例外**。§5.4 |

`traffic.rs` / `camera.rs` / `regulation.rs` は「std + ureq + serde_json のみ、`crate::` を参照しない」
方針だが、`serde` の derive を足してもこの方針は崩れない(外部crateである点は `serde_json` と同じで、
いずれも既に cargo 経由でしかビルドできない)。

### 5.4 カメラだけ「取得結果そのまま」にしない理由

`RoadCamera` は位置(`id`/`lat`/`lon`/`name`)のほかに `thumb_url` / `full_url` / `taken_at` を持つ。
これらは**15分ごとの撮影ディレクトリを含むURL**(実測 `.../20260816160000/811C200101.jpeg`)なので、
1時間後には404になる。保存すると「キャッシュから読んだのに写真が出ない」状態を作るだけなので、
**URL3項目は保存しない**。読み込み時は `thumb_url = None` / `full_url = None` / `taken_at = ""` になる。

その結果、キャッシュ由来のカメラに対して N キーを押すと、現状のコードは
`addr = "道路ライブカメラ: 画像URL無し"`(`ui.rs:317`)で終わってしまう。UI側の対応は §10.2 に書く。

同じ理由で、**交通量には `data_at` を分けて持つ**。JARTICの取得窓は
`[now-35分, now-25分]`(JST)なので、取ってきた直後でもデータ自身は25分以上前のものになる。
画面に出すべき経過時間は「取得からの経過」ではなく「観測からの経過」なので、
`data_at = fetched_at - OBSERVE_LAG_MIN×60` として保存し、表示はこちらを使う。

## 6. モジュール構成

新規3ファイル。`ui.rs` は現在2,353行あり、4レイヤの取得ブロック(約120行)はそこから出す。

### 6.1 `src/mesh.rs`(新規・std のみ)

JIS X 0410 のメッシュ計算。ネットワークにもcrateにも依存しないので単体テストしやすい。

```rust
pub fn primary_codes(lat_min: f64, lon_min: f64, lat_max: f64, lon_max: f64) -> Vec<u32>;
pub fn primary_bbox(code: u32) -> (f64, f64, f64, f64);   // (lat_min, lon_min, lat_max, lon_max)
pub fn secondary_codes(lat_min: f64, lon_min: f64, lat_max: f64, lon_max: f64) -> Vec<u32>;

```

`regulation.rs` が持つ private な `primary_mesh_codes()` は**そのまま残す**。あちらは
「bboxを受け取って自分でメッシュへ割る」という取得元の仕様に対応するために必要で、
`crate::` 非依存の方針も維持したい。重複する15行は、`mesh.rs` 側に
「同一bboxで両者が一致すること」を確認するテストを置いて担保する。

### 6.2 `src/plotcache.rs`(新規)

ディスク層のみ。ネットワークを知らない。

```rust
pub enum Layer { Traffic, Roads, Camera, Regulation }
impl Layer {
    fn dir_name(&self) -> &'static str;
    fn fresh_ttl(&self) -> Duration;
    fn stale_limit(&self) -> Option<Duration>;   // None = 無期限
    fn max_entries(&self) -> usize;
    fn max_bytes(&self) -> u64;
}

pub struct Cached<T> { pub items: Vec<T>, pub fetched_at: u64, pub data_at: u64 }
impl<T> Cached<T> { pub fn age_secs(&self, now: u64) -> u64; pub fn is_fresh(&self, l: Layer, now: u64) -> bool; }

pub fn load<T: DeserializeOwned>(layer: Layer, key: &str) -> Option<Cached<T>>;  // stale上限超過は None
pub fn store<T: Serialize>(layer: Layer, key: &str, items: &[T], data_at: u64) -> Result<(), String>;
pub fn gc();                    // 期限切れ削除 + 上限超過分の削除 + 旧バージョンdir削除
pub fn cache_root() -> Option<PathBuf>;
```

`T` に対してジェネリックにして、4種のデータ型を知らない状態に保つ。種別ごとの差(ディレクトリ名・
TTL・上限)は `Layer` に集約するので、値の一覧はこのファイルを見れば分かる。

### 6.3 `src/plotlayer.rs`(新規)

取得の段取り。`ui.rs` の4ブロックを置き換える。

```rust
pub struct PlotLayer<T> { /* セル表(key -> Cached<T>)・進行中ジョブ・ズーム下限・Layer */ }

impl<T> PlotLayer<T> {
    pub fn new(layer: plotcache::Layer, min_zoom: u32, cells_for: CellFn, fetch: FetchFn) -> Self;
    pub fn tick(&mut self, cx: f64, cy: f64, z: u32);  // 必要セル算出→不足ぶんのジョブ起動→結果受信
    pub fn items(&self, bbox: Bbox) -> Vec<&T>;        // 表示範囲でフィルタして返す
    pub fn oldest_age_secs(&self, now: u64) -> Option<u64>;  // ステータス表示用
    pub fn job_active(&self) -> bool;
}
```

- `cells_for`: bbox → セルキー列(`mesh::primary_codes` / `secondary_codes` / `nearest_bureau`)。
- `fetch`: セルキー → `Result<Vec<T>, String>`。この中で「まず `plotcache::load`、
  freshならそれを返す。staleまたは無ければネット取得して `plotcache::store`」を行う。
  つまり**ディスク読み書きは全部ワーカースレッド上**で起きる。
- 1レイヤの同時ジョブは今と同じく最大1本。1本のジョブは不足セルを**直列に**回し、
  1セル取れるたびに `mpsc` へ送る(部分的に描画が進む)。Overpass等に並列で投げない。
- 受信側は `Disconnected` を受け取るまでジョブを保持する。現状の受信コードも
  `Disconnected` を終了条件として扱っている(`ui.rs:979` 他)ので、形は変わらない。

## 7. 動作フロー

### 7.1 通常時

```
毎フレーム PlotLayer::tick()
  ├ z < min_zoom → 何もしない(既存セルは表示継続)
  ├ 必要セル = cells_for(視野bbox)
  ├ 必要セルが MAX_CELLS_PER_JOB 超 → 取得しない
  ├ 手元にありfresh なセル → そのまま使う(通信もディスクI/Oも無し)
  └ 不足/stale なセルがある & ジョブ未実行 → ジョブ起動
        ワーカー: セルごとに
          plotcache::load() が fresh → それを送る(通信なし)
          そうでなければ fetch → 成功: plotcache::store() して送る
                                失敗: staleがあればそれを送る / 無ければ失敗を送る
```

### 7.2 オフライン/取得失敗時

- 成功したセルだけが更新され、失敗したセルは**手元の値を保持する**。空で上書きしない。
- 起動直後で手元に何も無い場合は、staleでもディスクにあれば表示する(stale上限内のもの)。
- そのため `camera::fetch_cameras` と `regulation::fetch_closures` を
  **`Result<Vec<_>, String>` へ変える**必要がある。現状は失敗も0件も同じ `Vec::new()` で、
  呼び出し側から区別できない(§1.2(c))。関数内部では既にエラーを掴んでいるので、
  握り潰しをやめるだけで足りる。
- 通行規制はもう1つ変更が要る。今の `fetch_closures` は1回の呼び出しで
  「配信元パス発見HTML 1回 + メッシュJSON N回」を行う。セル単位で呼ぶと**HTMLを毎セル取り直す**ので、
  2段を分ける。

```rust
pub fn discover_json_base() -> Result<String, String>;              // 配信元パス(毎回変わる)
pub fn fetch_mesh(base: &str, mesh: u32) -> Result<Vec<ClosureEvent>, String>;
```

  1ジョブの中で `discover_json_base()` を1回だけ呼び、不足メッシュに使い回す。
  この配信元パスは**永続化しない**(更新のたびに変わるため、保存すると次回404になる)。

- カメラも整備局単位で取れるように変える。

```rust
pub fn nearest_bureau(lat: f64, lon: f64) -> u32;                   // pub 化
pub fn fetch_bureau(cd: u32) -> Result<Vec<RoadCamera>, String>;    // bboxで絞らない全件
```

  bboxでの絞り込みは `PlotLayer::items()` 側(メモリ上)で行う。

### 7.3 ロード・保存のタイミング(結論)

| タイミング | やること | 理由 |
|---|---|---|
| 起動時 | **何もしない** | `searchcache` のような一括ロードはしない。レイヤは既定OFF(`config.rs:91-93`)なので、使わない機能のファイルを読むことになる。必要なセルは初回 `tick()` のジョブが読む(数msなので体感は「起動直後から出ている」と同じ) |
| 取得成功のたび | **その場で該当セル1ファイルだけ書く**(ワーカースレッド内・ベストエフォート) | 書き込み頻度はTTLで抑えられている(交通量でも1セルあたり5分に1回)。まとめ書きにする理由が無い。強制終了しても失われない |
| アイドル時(#69) | `persist_full_state` は**変更しない**。代わりにGCの起動点として使う | 保存待ちのデータが存在しないので「フラッシュ」する対象が無い。一方GCはディレクトリ走査を伴うので、無操作中に回すのが都合が良い |
| 終了時 | 変更なし(`ui.rs:2349`) | 同上 |

アイドル分岐(`ui.rs:1259-1266`)は「ジョブが1本も走っていない かつ 60秒無操作」でしか到達しない
(`polling` が真の間は80msポーリング側へ行く)ため、GCが取得処理と競合することはない。
GCは**1セッション1回**、最初のアイドル到達時に別スレッドで走らせる(起動を遅くしない・
無操作のたびに走査しない)。

なお現状 `polling` の条件(`ui.rs:1251-1253`)に `major_roads_job` が入っていない。主要道路がまだ
描画されていないので実害は出ていないが、`PlotLayer` へ統合する際に4レイヤとも同じ扱いにする。

## 8. ディスク肥大化対策

### 8.1 構造で抑える部分

- キーが地理的に有界。カメラは全国でも**最大10ファイル**(整備局は10局)。
  交通量・通行規制は1次メッシュなので、日本全土を走破しても百数十〜二百ファイル程度。
- 同じセルは常に同じファイル名へ上書きされるので、同一地点に留まっても増えない。
- 増え方が読めないのは主要道路(2次メッシュ)だけ。全国では数千枚規模あり、1枚が都心なら
  数百KBになりうる。ここだけは明示的な上限が要る。

### 8.2 上限とGC

| 種別 | 最大エントリ数 | 最大バイト数 | 時間による破棄 |
|---|---|---|---|
| 道路交通量 | 200 | 20MB | 60分超(stale上限) |
| 通行規制 | 200 | 20MB | 24時間超(stale上限) |
| 道路ライブカメラ | 16 | 10MB | 無し |
| 主要道路 | 300 | 64MB | 無し |

合計の最悪でも約114MB。既存の `~/.config/termmap/tiles` が実測428MBあることを踏まえると、
アプリのディスク使用量の性格を変えない範囲に収まる。

`plotcache::gc()` の手順(ファイルの中身は読まない)。

1. `plot-cache/` 直下の `v1` 以外のディレクトリを削除する(バージョン移行の後片付け)。
2. 種別ディレクトリごとに `read_dir` + `metadata` で (パス, mtime, size) を集める。
3. stale上限を持つ種別は、mtimeが上限より古いファイルを削除する。
4. 残りをmtimeの古い順に並べ、エントリ数上限とバイト数上限の**両方**を満たすまで先頭から削除する。

真のLRU(最終参照時刻順)にしないのは、参照のたびにファイルを触ると mtime が
「取得時刻」の意味を失いTTL判定が壊れるため。キー空間が地理的に有界で、必要なセルは
どうせ再取得されるので、取得が古い順の破棄で十分と判断した。
(`searchcache.rs` がLRUなのは、検索キーワードという無限のキー空間を相手にしているから。)

## 9. UI への影響

### 9.1 経過時間の表示

ステータス行(`ui_status.rs:143-175`)の各レイヤ表記に、fresh を過ぎた値を出しているときだけ
経過時間を添える。fresh 以内のときは今までどおり変えない(常時表示すると情報量が増えるだけ)。

| 状態 | 現在 | 変更後 |
|---|---|---|
| fresh | `🚗12地点` | 変更なし |
| stale(表示継続中) | `🚗12地点` | `🚗12地点(32分前)` |
| stale + 再取得中 | `🚗12地点` | `🚗12地点(32分前)…` |
| ズーム下限より広域 | (取得して0件表示) | `🚗広域では非表示` |

交通量の経過時間は `data_at` 基準(観測からの経過)で出す。取得直後でも「25分前」と出るのが正しく、
これは実際にJARTICが出しているデータの鮮度そのもの(§5.4)。

通行規制は安全に関わるので、stale表示は色を落とす等で「今の状態とは限らない」ことが分かる形にしたい
(具体の見せ方は描画側の実装時に決める)。

### 9.2 カメラ写真(N キー)

キャッシュから読んだカメラは写真URLを持たない(§5.4)ので、N キーの動作を次のように変える。

1. 最寄りカメラに `full_url` があればこれまでどおり画像を取得する。
2. `full_url` が無ければ、まずその整備局を**その場で取り直して**URLを補い、続けて画像を取得する。
   ステータスは `📷カメラ情報を更新中…`。取得できなければ従来どおりのエラー文言にする。

リクエストは1回増えるが、**押したときだけ**になる。今は押す/押さないに関わらず90秒ごとに
整備局ページ(全カメラ入り)を取り直しているので、総量では大幅に減る。

### 9.3 レイヤON/OFFトグル

設定でONにしたときの `*_bbox = None`(`ui.rs:1493` 他)は不要になる。`PlotLayer` は
セル表が空なら次の `tick()` で取りに行き、キャッシュがfreshならディスクから即座に出す。
「ONにした瞬間に前回の内容が出て、必要なら裏で更新される」という動きになる。

TTLを無視した強制再取得の手段は今回は入れない。fresh が最長でも10分(規制)/5分(交通量)で、
待てば必ず更新されるため。`plotcache` 側には `invalidate(layer, key)` 相当を用意しておき、
必要になった時点でキーを割り当てる。

## 14. 正直な制約・未検証事項

- **通行規制の実際の更新周期は未確認。** 配信元パスの実測サンプルが
  `20260816154000` の1件だけで、10分境界に揃ってはいるが1サンプルから周期は決められない。
  fresh TTL 10分はデータの性質(数十分〜数日で変化)から置いた値で、実測に基づく値ではない。
  定数1個なので、実運用で配信周期が分かったら合わせる。
- **1セルあたりのレスポンスサイズは未計測。** 主要道路(2次メッシュ・都心)を数百KBと見積もったが
  実測していない。§8.2 のバイト上限は実測後に見直す前提の初期値。
  実装1段階目で `plotcache` の保存サイズをログに出して確かめるのが確実。
- **1次メッシュ全域を1リクエストで叩く負荷は未検証。** 交通量は現状z12で約56km四方を叩いており、
  1次メッシュ(約80km四方)はその延長線上だが、JARTIC側の応答時間は測っていない。
  `traffic.rs` が残す「範囲を絞らないとOOM」の実測は時間範囲についてのものである点に注意。
- **カメラの整備局割当は代表点最近傍のまま。** 管轄境界のポリゴンを持っていないので、
  境界付近のカメラは取りこぼす(現状と同じ制約)。キャッシュ単位を整備局にしても改善はしない。
- 交通量のディスク永続化は、4種の中で最も効きが薄い。stale上限60分なので夜を跨げば消える。
  このレイヤの主な利得は永続化ではなく fresh TTL 5分による通信削減(40回→12回)。
- ズーム下限を入れると、広域表示でレイヤが消える。これは今まで「重いクエリの代償で見えていた」
  ものを止める変更であり、機能の後退に見える可能性がある。段階2で実際の見え方を確認する。

| 箇所 | 設計 | 実装 | 理由 |
